RESEARCH NOTE / EVALUATION DESIGN

PROXY → VIDEO · CODE → WORLD

三种 evaluation，分别证明了什么？Proxy2World · Code World Model · Code Plans, Diffusion Renders

三篇都把显式世界或粗几何交给视频模型，但评测的重心不同：Proxy2World 衡量结构遵循与外观细化的取舍，CWM 验证离线原型是否可行，CoDeR 结合通用指标与功能场景演示。把它们放在同一张性能榜里，会丢掉最重要的实验条件。

01

先分开两个需要验证的环节

这类系统可以在代码里保存“门已打开”“物体移动到哪里”，再把这些状态渲染成视频。因此至少有两道问题：世界状态是否按规则正确变化，以及生成画面是否忠实表现这些状态。相机误差、画面质量和人工偏好回答的是其中一部分，不能自动代替代码正确性或任务成功率。

02

Proxy2World：把遵循与细化分开测

Proxy2World: Learning to Generate Worlds from Lightweight Proxies without Seeing Them · arXiv:2609.35023

粗代理只给出布局和运动，不提供完整外观。它的评测围绕一个很具体的取舍：输出既要按 proxy 行动，又要摆脱低模、平面纹理和僵硬细节。所以论文没有只用一个画质总分，而是并列检查几何、相机、结构遵循和细化效果。

25场景，15 个中型 + 10 个大型300段五秒序列，基准总量78段序列，实际评测集

每个测试样本给什么，输出检查什么

ProxyBench 为每例准备粗场景、目标相机轨迹、同步 proxy 渲染、文本及参考首帧。方法接收其中自己支持的条件，生成视频后再评测。参考首帧并非所有基线都使用；T2V 与带首帧的 TI2V 条件应分开阅读。

03

Code World Model：验证原型链路能走通

Code World Model: Coding Agent as World Brain · arXiv:2608.25927

这篇把“代码管理世界、视频模型实现视觉”作为系统方向，实验主要回答这套接口能否在若干具体场景中工作。它已经串接了离线的代码 → proxy → 视频链路；证据重点是展示效果，而非建立一套完整的量化基准。

agent 构建可控世界→用户操作并录制 proxy→离线生成视频→比较动作、布局与风格
INPUT / 条件

为同一段行为准备三种提示

在现成引擎或 AAA 游戏模板上构建世界，记录逐帧 proxy；再配上 agent 给出的结构化文本，以及 GPT Image 2 生成的外观锚图，交给 MiniMax H3 Ref2VA 离线生成。

OBSERVATION / 检查目标

看结构是否保留，外观是否可改

对照生成画面与 proxy，观察实体位置、动作、场景布局和相机跟随；通过不同外观或风格展示同一结构条件下的视觉变化。

结果的证据形式

  • Fig.4 展示 5 组案例，每组展示 6 个时间点。这是论文选出的展示面板，不是已报告的测试集规模。
  • 与 WorldPlay、Matrix-Game 3.0、LingBot-World 2.0 的比较主要是项目页定性视频；论文明确不把推理延迟纳入比较。
  • 没有报告统一的定量指标、人工研究、正式消融或交互任务成功率。训练用的 9,420 个 clips / 约 5.6 小时也不能当作测试规模。
证据范围

离线链路可行已有展示；“把生成视频反馈给 agent，再修改代码并实时继续运行”的闭环，尚未得到相应评估。两者是不同层次的验证目标。

论文报告与边界：Code World Model §4、Fig.4、§5。

04

CoDeR：自动指标与功能演示并行

Code Plans, Diffusion Renders: Open-Ended Generative World Modeling · arXiv:2609.26458

CoDeR 的评价覆盖面更广：用 WorldScore 测生成输出，用消融检验两个设计，再以专门场景展示记忆、交互、画外演化与多智能体。最后加入人工评分，连接自动读数与观看体验。

先把 benchmark 输入转换成白盒世界

原始首帧→SAM 3 分割 + 深度估计→GPT-6 Astra 重建白盒→生成并评分

深度来自 Depth Anything V2；生成还以原始首帧为条件。这是从图像重建的白盒，不是 benchmark 提供的真值 3D。代码世界可以提供其内部精确的几何与相机，但重建几何可能与原始画面存在偏差。

06

借鉴时，把评测拆成能定位问题的几层

如果要为自己的“代码世界 + 视频渲染”系统设计 evaluation，可以沿用 Proxy2World 的双目标思想、CWM 的接口验证和 CoDeR 的功能场景，再补上各层之间的独立检查。下面是本文的设计建议，并非三篇已经完成的实验。

  1. 先锁定输入与测试单元

    记录是否给首帧、深度、相机、文本；固定同一批场景与动作序列。把训练规模、基准总量、实际测试量分别列出。

  2. 把“遵循”与“好看”分别打分

    前者测轨迹、实体位置、动作完成和布局；后者测画质、合理细节和偏好。放在同一张结果表里，显式呈现取舍。

  3. 长期能力用回访和画外事件测试

    规定离开多久、回来比较什么；同时读取代码状态与画面中的状态，让“记住了数值”和“正确画出来”各有判据。

  4. 交互能力用任务成功率和运行成本补齐

    统计生成世界是否能运行、规则是否正确、动作是否成功，再报告用户输入到画面更新的延迟。通用画质指标不能独自回答这些问题。

共同阅读结论

三篇分别提供了有价值的评测片段。它们仍没有系统地把代码生成成功率、规则正确性、交互任务成功率与生成画面质量放在同一套实验里量化；这正是下一套评测可以补上的连接。
