LynnReal-Omni

与其为每种控制造一条支路，不如把参考图、3D 渲染、游戏录屏和历史全部改写成同一种「带标签的 token 行」

扩散视频模型好看但不听话；agent 写的 3D 场景和小游戏听话但不好看。 LynnReal-Omni 的赌注是把两边接在一根总线上：让 agent 负责「世界里发生了什么」，让视频模型只负责「它看起来什么样」。 实现方式朴素到有点无聊——在 MiniMax-H3 这个已经会联合生成音视频的 50 层 DiT 上， 给每一行 token 补四个字段（模态标签 · 行内索引 · 3D RoPE 坐标 · 该行自己的噪声时刻）， 于是 外观参考图、逐帧对齐的 pose / 深度 / 游戏录屏、压缩过的历史 latent 就能塞进同一个序列而不互相冒充。整篇论文真正的工程量在后面三件事上： 四步蒸馏、Flash 把中段 26 层的空间 token 砍到约 1/4、把 36 层 VAE 解码器蒸成 26 层—— 因为少步蒸馏之后，瓶颈已经从去噪器挪到了解码器。

全篇可以压成一句话：凡是想让视频模型知道的事，都写成「一段 latent + 它属于哪个模态 + 它在哪个时空坐标 + 它现在有多脏」， 然后当作普通 token 行排进同一个序列。点标签逐段看。

一句话抓住这篇的立场

它不认为视频扩散模型该去学物理。它认为物理应该由 agent 写成可执行程序（网格、碰撞、状态更新、相机轨迹）， 视频模型只做一件事：把这份粗糙但正确的运动，渲染成好看的像素。 论文里那句「agent 构建轻量场景或可玩原型，由快速视频扩散模型提供细节外观」就是全文的论点。 所以它的核心技术贡献其实不是「世界模型」，而是一个足够快、接口足够统一的可控渲染器。

01The four gaps

它在解什么问题：四个同时成立的缺口

论文引言点了四个缺口。前三个是老生常谈，第四个才是这篇最有信息量的观察。

GAP 1 · 任务割裂
每个任务一条流水线
T2V、V2V、图像条件、参考引导、结构控制、编辑、长视频各自演化。 agent 要串多个模型和一堆临时接口，工程成本高，跨任务行为还不一致。 LynnReal 的答案：一个去噪器 + 任务特定的输入排布。
GAP 2 · 长程漂移
越拍越不像
外观漂移、身份改变、光度伪影。论文引的是 Self-Forcing++、Self-Forcing、Reward Forcing 这条线。 答案：固定 head 帧 + 有界历史，让注意力开销与视频长度无关。
GAP 3 · 评测不全
VBench / VideoPhy 拆不开的维度
多镜头连续性、动作绑定、物理合理性、可控性、音频质量没有被同一套协议覆盖； 而且不同量纲的指标被平均到一起，会把某一维的失败藏起来。答案：自建 MSAVP。
GAP 4 · 解码瓶颈 ★
少步蒸馏之后，慢的是 VAE 不是 DiT
这是全文最值得记住的一句：大家默认成本在去噪 transformer 上，但几步蒸馏把去噪成本砍掉之后， 主导成本变成了 VAE 解码器。所以解码器加速是必须的，而且必须和去噪一起测—— 减少解码计算会影响时间相位或重建质量。
这个观察在它自己的表里被证实了

540p / 22 帧、未做解码优化时：Standard 的 DiT+解码是 1268 ms，其中换上轻量解码器 + 自适应分块 + 编译之后整条链降到 843 ms—— 解码那一段从约 469 ms 压到约 119 ms。Flash 更极端：它的 DiT 只要 262 ms，而未优化的解码器本身就比整个去噪还贵。 换句话说，Flash 这种三步模型如果不换解码器，省下来的去噪时间基本白省。

02Native task representation

原生任务表征：四个字段，一条序列

这是整篇的地基，也是它相对「给每个任务加 adapter」路线的全部差异。 每一行 token 都携带模态标签、模态内行索引、3D 旋转位置、这一行自己的噪声时刻。 文本与视觉上下文先编码好，去噪器一次前向同时吐出视频速度和（若有）音频速度。

row  =  ( modality tag , row index , τ, y, x , trow ) §4.2 modality tag：视频 / 音频 / 文本 / 控制。　row index：模态内部的顺序，保证参考图的先后不被打乱。　 (τ,y,x)：3D RoPE 坐标——注意 τ 不是"第几帧"而是连续时间轴上的位置。　 trow：每一行独立的干净时间。条件行可以是干净的（t=1），目标行是脏的，两者在同一序列里并存而不冲突。
损失只在「任务的有效目标行」上算：条件行和补齐的目标行被排除。

2.1Δ > 0：让参考和目标待在不同的域里

逐帧对齐的控制（pose 序列、编辑源、深度序列、游戏渲染）与目标共享完全相同的 latent 几何与空间网格。 唯一的区别是时间坐标上的一个常数偏移：

τtargeti − τcontroli = Δ ,  Δ > 0 Eq.1 论文特意强调：如果把两者的绝对 RoPE 坐标设成相等，会改变模型的条件语义。 也就是说「对齐」不是靠坐标相同实现的，而是靠一个恒定的正偏移——模型学到的是「往前看 Δ」这件事。 代码里可以直接读到这个常数：framepack.py 把目标行的时间坐标做 += 4 * _ROPE_FRAME_RESCALE。

论文自己划的红线：接口区别 ≠ 像素级还原

原文写得很克制：「This interface distinction is not a guarantee of pixel-exact image reconstruction」。 也就是说，即便用原生关键帧接口把首帧写进目标分区，输出第 0 帧也不保证等于输入图。 §5.5 的湖面编辑例子也是同一口径：改天气那组「合成了被雾遮住的细节」，属于生成式编辑，不是从成对干净图里恢复，所以论文明确拒绝报 restoration PSNR。这点很诚实。

03Two clocks, four steps

两个时钟，四步走完：视频和音频不在同一个「脏度」上

这是论文里最容易被跳过、但其实最值得拆的一节。 视频和音频共享同一次去噪评估，却各自走一条噪声时间表。 论文给了两条公式和一组数字，但没说它们是怎么来的——下面是我复原的结果，并且能对上小数点后四位。

zt = t z + (1 − t) ε ,   v⋆ = z − ε Eq.2 clean-time 约定：t=1 是干净、t=0 是纯噪声，和常见的「t 越大越脏」相反，读表时容易看反。 噪声水平 s = 1 − t。速度目标 v⋆ = z − ε 与时间坐标的重参数化无关。

3.1训练时的噪声分布：logit-normal 再 shift 3

u = Sigmoid(g), g ∼ 𝒩(0,1)  ⟹  sv = 3u / (1 + 2u) Eq.3 这就是 flow matching 里的标准 shift：shiftk(s) = k·s / (1 + (k−1)s)，这里 k = 3。 把 logit-normal 采到的 u 往「更脏」的一侧推，让训练更关注高噪声段。

3.2音频时钟：论文的两步映射其实就是「撤掉 12，换成 3」

sb = sv / (12 − 11sv) ,   sa = 3sb / (1 + 2sb) Eq.4 第一步是 shift1/12，第二步是 shift3。shift 可复合（shifta∘shiftb = shiftab）， 所以整条映射等价于一句话：sa = shift1/4(sv)。 也就是说，视频用 flow shift 12、音频用 flow shift 3，二者共用同一个随机抽样 g、同一个均匀步格， 只是把同一个格点推到了不同的噪声水平上。视频与音频各自独立采高斯噪声。
我的复原（论文没写，但能对上）

论文只给了推理时的干净时间：视频 (0, 0.0270, 0.0769, 0.2000)，音频 (0, 0.1000, 0.2500, 0.5000)，并说「这些值由模态各自的 row-to-time 映射决定，不是去索引同一个时间步向量」。 把它们反推成噪声水平 s = 1 − t，会发现两串数字都落在同一个均匀 5 点格 {1, 0.75, 0.5, 0.25, 0} 上，只是 shift 不同：

shift12(0.75) = 9/9.25 = 0.97300 → t = 0.02700 ✓　　shift3(0.75) = 2.25/2.5 = 0.90000 → t = 0.1 ✓
shift12(0.50) = 6/6.5 = 0.923077 → t = 0.076923 ✓　shift3(0.50) = 1.5/2 = 0.75 → t = 0.25 ✓
shift12(0.25) = 3/3.75 = 0.80000 → t = 0.2 ✓　　　shift3(0.25) = 0.75/1.5 = 0.50 → t = 0.5 ✓

3.3损失：音频只占 0.1，而且「没有音频」不等于「静音」

ℒ = MSEV(ṽv, zv−εv) + 0.1 · 𝟙valid audio · MSEA(ṽa, za−εa) Eq.5 论文特意写了一句 “Missing audio is not treated as a supervised silent recording.”—— 缺失音频靠 mask 排除，而不是当成「监督为静音」。这和数据侧「确认无人 ≠ 检测器失败」「asset 标记为 available / not applicable / blocked」是同一种洁癖， 也是整篇最让我信任的工程习惯：把「没有」和「是零」分开记。

3.4把 CFG 烤进权重：推理时不再跑无条件分支

ṽ = [ vc + (w − 1)·sg(v∅) ] / w ,   w = 3 Eq.6 同一个去噪器额外给出一个去掉文字、但保留全部视觉控制的 stop-gradient 预测 v∅， 只有条件分支拿梯度。在回归最优点上这会逼出 vc ≈ w·v⋆ − (w−1)·v∅， 即把 CFG 的外推提前写进了条件分支本身。推理时直接用条件预测，每步不再加一次无条件前向。
这里有个容易被忽略的语义：guidance 只作用在文字上

v∅ 是「captionless but retaining the supplied visual controls」。所以被放大的只是文本条件的贡献， 参考图、pose、游戏录屏这些视觉控制在两个分支里都在。这意味着：你不能靠调 guidance 强度来加强/减弱视觉控制的服从度—— 而且 w=3 是训练时写死的，推理端没有旋钮。要改控制强度只能改提示词或换控制信号本身。

3.5少步蒸馏：低秩 TDM + 一个全深度的假分数 critic

Standard 保留完整骨干，用低秩轨迹分布匹配（TDM）训到 4 次评估。训练在 4 个不重叠的转移区间上进行， 每次只对其中一个被选中的学生转移反传。一个冻结的 teacher 和一个单独训练的全深度 fake-score critic 在「以学生端点为条件采样出来的噪声态」上评估。critic 用带裁剪信噪比加权的重要性加权干净目标回归来训； 学生用下面这个归一化 pseudo-Huber 代理：

ℒDM = mean[ ρc( zG − sg(zG − d) ) ] / sg(a) ,  ρc(e) = √(e² + c²) − c Eq.8 d = ẑF − ẑT（critic 与 teacher 的干净预测之差），a = max(mean|zG − ẑT|, 10−6)，c = 10−3。
看懂这行的关键在 sg：z_G − sg(z_G − d) 的数值恒等于 d，但梯度是 ∂/∂zG = 1。 于是它做的事是「在 d 这个点上取 ρc 的导数，然后把这个导数当作 zG 的梯度回传」—— 这就是 DMD 那一族的经典写法：用两个分数之差当梯度方向，用鲁棒函数把它压住，再用 a 做自适应归一化。 归一化放在鲁棒惩罚外面，所以它只缩放步长、不改变饱和点。

另外两点值得记：

  • Reward Forcing 的动态奖励被接了进来，但只重加权视频项；音频项拿固定权重，理由很实在——奖励模型不懂音频。
  • 部署只要学生的 EMA，teacher 和 critic 都不需要。这也是为什么发布的 bundle 里只有一个 DiT。
  • 训练时视频 shift 是 3（Eq.3），推理时视频 shift 是 12。这个训练/推理的 shift 不一致是 H3 系的惯例，不是笔误，但论文没解释。
04Flash

这里有本文最硬的一处自相矛盾：W4A8 还是 W8A8？

方法节 §4.3.1 的最后一句写的是：「The final Flash DiT adopts W4A8 quantization—INT4 weights with FP8 activations」。 但实验节的表 6 那一行叫 “+ W8A8 projections”，§5.4 说完整加速路径是 W8A8，且「Flash 全程保持它训练好的 INT8 checkpoint」； 仓库 README 写「Flash · W8A8 DiT（INT8 权重 + INT8 激活）」；HF 模型卡也写 W8A8。

05Bounded history

长视频：固定一帧当接缝，历史压进一个恒定 token 预算

这一节是论文里与代码吻合度最高的一节——我按 model/framepack.py 把预算算了一遍， 数字卡得很紧，几乎可以肯定是照着 token 预算反推出来的设计，而不是事后描述。

5.1块式生成：17 帧一块，接缝那一帧被钉死

每一块的流程是：把上一块最后一帧 RGB 当成共享边界帧，它的 latent 在去噪中保持不变； 模型预测 5 个未来 latent；边界 latent 与这 5 个一起联合解码成 18 帧 RGB； 去掉那一帧重复的边界，交付 17 帧新画面。每块 4 次去噪评估， 不做帧插值、不做曝光校正。

为什么是 17 和 5？因为 H3 codec 的对齐契约是 17n + 5 帧 ↔ 5n + 2 个 latent 帧。 这个关系在代码里是明写的：rgb_capacity = 17 * ((capacity − 2) // 5) + 5。 检验一下：bootstrap 是 7 个 latent ↔ 22 帧 RGB（n=1）✓； 论文 15 秒测试里说「显式允许 362 个计算帧、保留前 360」——362 = 17×21 + 5 ✓，对应 107 个 latent 帧。 所谓「native temporal padding」就是把请求帧数向上对齐到这个格子。

06Decoder distillation

轻量解码器：36 层蒸成 26 层，latent 接口一动不动

6.1训练分布：0.6 真实 latent + 0.4 生成 latent

这是整节最重要的设计：学生要解码的不只是「编码器编出来的 latent」，还有生成模型真实吐出来的 latent—— 两者的分布并不相同。所以 p=0.6 用 z = E(x)，p=0.4 用生成 latent。 生成 latent 没有成对像素目标，只能由 teacher 重建 yT = DT(z) 监督。 此外还有 p=0.25 的高斯扰动（相对标准差 0.03）来提升对「偏离编码器分布」的鲁棒性，同样由 teacher 监督； p=0.1 抽单帧 latent 切片强化图像解码。

真实数据分支里，native-HD（短边 ≥720）与高运动样本各以 0.2 概率抽取，≥20 fps 的视频以 0.7 概率密集采样； 每段 2–33 帧，受 400 万「像素×帧」预算约束。图像样本还有一个专用图像解码器 DI： 生成的图像 latent 由 DI 监督；对编码的训练图像则按重建保真度择优—— DI 的裁剪重建若 L1 更低就取代 DT。

10Open questions

我的存疑清单

先说结论：这篇报告的自我约束是我近期读到最好的之一——它反复拒绝把重建指标当生成质量、把小画布计时当大画布速度、把一次成功的编辑当物理修复。 下面这些问题不改变我对它工程质量的正面判断，但会改变你怎么引用它的数字。按严重度排序，点开看依据。

筛选：
D1高方法节说 Flash 用 W4A8，但发布与全部延迟数都是 W8A8▸
论文写了什么
§4.3.1：“The final Flash DiT adopts W4A8 quantization—INT4 weights with FP8 activations—to further reduce memory traffic and accelerate matrix multiplications.”
其他地方写了什么

表 6 的行名是 “+ W8A8 projections”；§5.4 说完整加速路径是 W8A8，并写「Flash 全程保持它训练好的 INT8 checkpoint」； 仓库 README 与 HF 模型卡都写 W8A8（INT8 权重 + INT8 激活）；script/sample/README.md 写「Flash uses its packaged W8A8 projections (INT8 weights and INT8 activations), with BF16 sensitive layers」。

代码里是什么

model/int8.py 的 quantize_transformer() 直接返回 {"format": "W8A8", ...}，逐 token 激活尺度、逐输出通道权重尺度、首尾各 1 层不量化、AdaLN/refiner/IO 不量化。 model/w4f8.py 则确实实现了 INT4 权重 + FP8 激活（fbgemm f8i4bf16_shuffled，仅 Hopper），pipeline.py 有 quantization == "w4f8" 分支。

我的判断

W4A8 不是虚构，它是一条已实现但未随本次 beta 发布、也没有任何一行实测覆盖的路径。 风险在于：方法节把它写成「final Flash DiT」，读者会默认表 6/7/8 的 Flash 数字来自 W4A8。实际全部来自 W8A8。 建议作者把这句改成「we additionally implement W4A8；本报告的测量均在 W8A8 下进行」。

D2高摘要与引言的核心延迟数字互相冲突，而且都不是同一个口径▸
两处原文
摘要：“…warm generation and decoding of a 22-frame 540p video take 843 ms with LynnReal-Omni and 377 ms with Flash.”

引言：“…with warm generation and decoding of a 22-frame 540p video taking 909 ms on one H100 for LynnReal-Omni and 591 ms for Flash.”
表里是什么

表 6 末行与表 7 首两行：DiT+解码 843 / 377 ms，生成 wall 959 / 479 ms。 仓库 script/sample/speed_test/README.md 另给了一组独立扫参结果：829.3 / 371.5 ms（wall 919.1 / 462.6）。 装机验证（表 8）是 857 / 383（wall 957 / 477），公开命令跑出 855 / 381（wall 940 / 458）。

我的判断

909 / 591 对应不上任何一行，疑似早期版本的残留（Flash 的 591 尤其可疑：从 377 到 591 是 57% 的差距，不像口径差异）。 另外摘要用「generation and decoding」描述 843/377，但这两个数其实是 DiT + 视频解码器的 CUDA 时间， 不含调度、音频解码、RGB 转换与输出传输——那才是 959/479。 引用建议：说「DiT+解码 843/377 ms、端到端生成 959/479 ms（单 H100、540p、22 帧、warm）」，并注明这是 W8A8 + FA3 + 编译轻量解码器 + 自适应分块的完整路径。

D3高「real-time world model」这个自我定位，自家延迟表支持不住▸
论文怎么说
§5.2.3：“Unlike the offline generators in the comparison, LynnReal-Omni is designed as a real-time world model… its low-latency interactive design retains competitive instruction and visual-world fidelity rather than trading them away wholesale for speed.”
自家表怎么说

MSAVP 跑的是 15 秒、1280×720。表 7 里 768p 15 秒：Standard 生成 wall 122.9 s、Flash 40.4 s—— 分别是播放时长的 8.2× 与 2.7×。只有 540p / 22 帧（0.917 s 画面）时 Flash 的 479 ms 才快过实时。

还有两个结构性障碍
  • Flash 不能续写。model/continuation.py 明确抛错 dense continuation requires the standard unified transformer；论文也说 Flash 加速的是 T2V 与原生关键帧条件生成。所以流式路径只能用更慢的 Standard（540p 每块 959 ms 对 0.917 s 画面，约 1.05× 实时，即略慢于实时）。
  • 发布默认的流式还要更贵。超过 136 帧后每块 4+2 步，且单卡上文本条件刷新要把编码器过 CPU，README 明说「increases end-to-end latency」。
公平地说

论文结论里其实自己收了口：「current warm 540p measurements demonstrate useful acceleration but do not establish equivalent native 768p speed or live-interaction latency」， 并把「记录 action-to-display 时间的更长交互轨迹」列为未来工作。所以问题不在诚实度，而在正文里那句 “real-time world model” 与结论口径不一致—— 引用时请按结论那句来。

D4中MSAVP 指标数：摘要说 20，引言说 25▸

摘要：「a 100-prompt, 20-metric evaluation design」。引言第四个 bullet：「MSAVP, a 100-prompt, 25-metric benchmark」。 表 5 明确列出 20 项，六族分别是 3 / 3 / 4 / 3 / 3 / 4 = 20；表 2、表 4 与图 6 也都写 20。 引言的 25 是错的。

同一处还有更麻烦的一点：能力族被叫了三套名字
  • 摘要给的是五个轴：instruction following / world plausibility / visual quality / temporal behavior / audio coordination。
  • 引言给的是另一组六个：semantic alignment / visual quality / temporal consistency / physical plausibility / controllability / audio quality。
  • 表 5 与 §5.2.3用的是第三套六族：Prompt Fidelity / Event Execution / Visual Quality / Multi-shot Coherence / World Plausibility / Audio Alignment。

「controllability」和一个独立的「temporal」族在表里与计分里都不存在；反过来 Event Execution 与 Multi-shot Coherence 在两段摘述里都没出现。 这和 20 / 25 的出入大概率是同一份旧稿留下的。以表 5 为准。

D6中论文方法节描述的流式策略，不是仓库的发布默认▸

§4.4.1：「Each chunk requires 4 denoiser evaluations, without frame interpolation or exposure correction.」表 2 也记为「四次评估每块」。

但 README 与 test/streaming.md 的默认是：超过 136 帧后启用 context refresh——bootstrap 与前 7 个续写块各 4 次； 第 8 个续写块起 4+2 次（第二遍对第一遍的干净 latent 加独立高斯噪声，用原调度尾部 sigma [0.92307693, 0.8, 0] 再走两次前向）， 并把上一块交付画面的首末帧编码进文本上下文。30 秒默认 242 次前向；论文描述的那条是 --no-refresh-context 的 172 次。

更值得注意的是接缝本身的定义也不一致

§4.4.1 描述的是单个共享边界：「the final RGB frame of the preceding chunk is reused as a shared boundary frame. Its latent remains fixed … the duplicated boundary frame is then removed.」 但 test/streaming.md 写的是两个：「predicts five new latent frames per chunk while fixing the last two history latents」，并且「retains the decoder's five-frame overlap」「The two fixed overlap latents and decoder overlap remain unchanged」。 代码侧也对得上这一版：model/stream.py 的 rgb_capacity = 17 * ((capacity − 2) // 5) + 5 里那个 −2 就是两个重叠 latent， causal_stream.py 里 self.target_latents = 5（而 framepack.continuation_layout 的默认是 6 = 1 head + 5）。 只读 §4.4.1 会实现出一个和发布版不同的接缝。

此外论文 §4.4.2 的历史策略（1 密集 + 2×stride2 + ≤8×stride4）与 framepack.history_plan 默认完全吻合， 但发布流式在前 7 块用的是「4 个密集 sink」，第 8 块起才降到 1 个。论文描述的是方法，仓库默认是方法 + 一堆抗漂移补丁，两者都成立但不是一回事。 做复现或对比时必须写清楚用的哪条。

D7中“Temporal repair” 其实是逐帧独立图像编辑▸

§4.6 的机制：对每一源帧独立调用图像编辑接口、跨帧用同一个 seed、然后按原顺序拼回； 每帧内部先生成一段 22 帧的短片再选其中一帧。成本是 4T 次评估（120 帧 = 480 次）。

论文自己把话说尽了：「the frame edits are independent and impose no explicit cross-frame consistency constraint」「Temporal consistency remains a limitation of independent frame editing」， 并且承认残留亮度与形状波动、火焰高度变化减小。所以问题只在命名：叫 temporal repair 会让人以为有时域建模，实际只有「保持帧序与播放时序」。

另外一个小的不一致：论文说该次运行「选每段 22 帧内部片段的最后一帧（index 21）」，而 README 说默认选 index 11（可用 --image-frame 改）。两处都不算错，但默认值不同，复现时会差一截。

D8中骨干维度自洽性：width 5376，但 56 heads × 128 = 7168▸

§4.2：「Its residual width is 5,376, with 56 attention heads of dimension 128 and a feed-forward width of 14,336.」

注意 56×128 = 7168 ≠ 5376。这不一定是错的——QKV 投影维度大于残差宽度是可行设计（过完备注意力），而且这么算参数量才凑得到 32B 量级。 但 5376 = 42×128 也成立，56×96 = 5376 同样成立，所以到底是「56 头 ×128」还是「42 头 ×128 / 56 头 ×96」需要看 config.json 确认。 论文没有给出任何一句解释，而这是复现者第一眼就会卡住的地方。

顺带：参数量口径也对不齐——论文写 32B / 27B（Flash），HF 模型卡显示 33B / 28B。 而且 27B ≈ 42/50 × 32B 是按层数线性外推的结果，但 Flash 只删了 block、没删 embedder 与 codec，线性外推并不严格。

D9中表 6/7 的 Standard 行用 W8A8，但「Standard DiT INT8」在 README 里是 coming soon▸

README 明写：「Standard DiT INT8 is coming soon. Experimental Standard INT8 launchers are already in the codebase; the downloadable checkpoint has not been released.」

好消息是这不构成不可复现：pipeline.py 在 int8=True 且 bundle 本身不是 int8 时，会调用 quantize_transformer() 在加载时做训练后量化（PTQ）， 所以 script/sample/standard/int8/*.sh 现在就能跑。

C术语速查

原生任务表征（native task representation）
每行 token 携带「模态标签 + 模态内行索引 + 3D RoPE 坐标 + 本行噪声时刻」的打包方式。它是这篇统一各任务的唯一机制：没有 adapter、没有 ControlNet 支路，全靠标签和坐标区分身份。
Δ > 0 的时间偏移
逐帧对齐控制与目标共享空间网格，但时间坐标差一个恒定正值。论文强调把它设成 0 会改变条件语义——模型学的是「往前看 Δ」。代码里是 += 4 * _ROPE_FRAME_RESCALE。
clean-time 约定
t=1 干净、t=0 纯噪声，σ = 1 − t。读表时最容易看反的地方。
flow shift
shiftk(s) = ks / (1 + (k−1)s)，把均匀步格推向更脏或更干净的一侧。本文视频用 k=12、音频用 k=3；训练时视频的噪声分布用 k=3。
TDM（轨迹分布匹配）
少步蒸馏的一种：不匹配最终样本分布，而是让学生的短转移分布对齐教师在同一区间上的分布。本文在 4（或 3）个不重叠区间上训练，每次只反传一个被选中的转移。
fake-score critic
DMD 家族里那个「学生分布的分数模型」。这里是全深度的、单独训练的，用带裁剪 SNR 加权的重要性加权干净目标回归来训。部署时不需要它。
共享边界帧 / 固定 head
续写时把上一块最后一帧 RGB 的 latent 钉死当作条件，与 5 个新 latent 一起解码，再丢掉重复的那一帧。用来保证块与块之间没有跳变。
有界历史（bounded history）
历史 latent 按「1 个密集 + 2 个 stride2 + ≤8 个 stride4」压缩，总 token 数不超过 2 个全分辨率 latent 帧；存储侧满了就保留最初与最近、丢掉中间。
MSAVP
本文自建的多镜头音视频物理基准：100 条提示、20 指标、6 个等权能力族，先冻结打分清单再看视频。
W8A8 / W4A8
权重 8 位 + 激活 8 位 / 权重 4 位 + 激活 FP8。发布与全部测量用前者，方法节写的是后者（D1）。
