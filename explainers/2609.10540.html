Programmable World Model

与其教视频模型「记住」世界，不如把世界记在别处，只让它负责画

现在的交互式视频世界模型有一个共同的软肋：世界现在是什么样，只存在于生成上下文里。 你没法点名某个实体，没法查一个已经转出画面的东西还在不在，更没法规定「门在什么条件下才开」。 这篇的做法很干脆——把状态整体搬出去：一个 coding agent 把自然语言写成可执行的世界程序， 一个轻量引擎按规则逐步推进一份权威世界状态（含离屏实体和 HP、阵营这类看不见的量）， 一个确定性编译器把状态里可见的部分沿目标相机投影、光栅化成三张像素对齐的控制图， 最后交给一个冻结的视频模型当渲染器。 代价也同样干脆：这个「世界模型」不再预测世界，它渲染一个被写好的世界——这既是它 94% / 98% 的来源，也是读这篇论文时最需要拿捏的地方。

00One Figure

一图看懂：一次交互，三段流水线

论文 Eq.(3) 把整个系统压成了一行。读懂这一行，方法部分就读完了一半： 引擎推状态 → 编译器投影 → 渲染器出画，三段里只有最后一段是神经网络，前两段是普通程序。

st  ——F, at —▸  st+1  ——P, Ct+1 —▸  Mctrlt+1  ——G —▸  It+1 Eq.3 F：轻量引擎的状态转移，纯程序，按规则执行，不学习。　P：确定性状态编译器，把世界状态在目标相机 Ct+1 下投影成控制图，不改变状态。　G：生成式渲染器，唯一的神经网络部分。　注意 Ct+1 是输入而不是输出——相机轨迹由玩家/系统给定，模型不预测它。
一句话抓住这篇的取舍

其他世界模型是「让神经网络同时负责记住和画出」；这篇是「记住交给一段你能读懂的程序，神经网络只负责画出」。 于是状态一致性从「训练目标里希望它涌现出来的性质」变成了「工程上保证的性质」—— 但世界的动力学也从「学出来的」变成了「你手写的规则」。引擎不做物理，只做规则。

01Motivation

它到底在补哪三个洞

Introduction 列了三条，值得逐条落到具体场景上——因为后面所有设计都是这三条的直接产物。

洞 1 · 寻址
你没法点名一个实体
现有控制接口给的是相机、按键、整句 prompt。「让左边第二个人倒下」这种指令，只能靠文本描述去撞， 撞中了也不是一个可复用的句柄——下一步你还是不知道该怎么再指到他。
洞 2 · 持久
没有独立于当前视角的全局状态
转过身，刚才那三个人还在不在？他们的血量呢？离屏实体和 hp / 库存 / 任务进度 / 交互历史 这类根本不会出现在像素里的量，在纯生成式世界里只能寄希望于上下文没忘。多人场景下这条更致命。
洞 3 · 规则
你写不了「规则」，只能写「愿望」
论文这句话说得很准：prompt 一个想要的结果，并不等于确立了一条此后一直生效的可执行规则。 「门在拿到钥匙后才开」不是一次生成，是一个约束，得在后面每一步都成立。

三个洞指向同一件事：缺一份账本。而一旦决定把账本单独拿出来，立刻就有一个新问题—— 账本长什么样，才能既让程序方便读写，又足够指挥得动一个视频生成模型？这就是全文的中心问题，也是下一节。

02Representation

表征取舍：为什么偏偏是 3D OBB

论文 §2 花了整整两页只论证一件事：接口该做多细。这一节是全文最有价值的部分， 因为它给了一个我以前没见人这么讲清楚的判据——训练和推理是从两个相反方向拿到同一个表征的。

训练： 已实现的动态  —▸  结构表征 Eq.1
推理： 高层状态转移  —▸  结构表征  —▸  生成的动态 Eq.2 训练时，视频里的动作已经发生了，你只是从像素里把它测出来（检测、跟踪、深度）。 推理时反过来：你只有一句「他中弹倒地」，必须先造出这条随时间变化的结构轨迹，生成模型才有东西可依。 表征越细，你在推理端要凭空造的自由度就越多。「说他要倒下」很容易，「给出他每一帧的骨骼姿态」是另一个课题。

选定 OBB 之后，「什么归你管、什么归模型管」就有了一条清楚的分界线：

显式指定（编译器负责）
实体级、世界系、可重投影的骨架
  • 位置 / 尺寸 / 朝向：共享世界坐标系下的一个 OBB，固定的一小组几何参数
  • 持久身份：跨遮挡、跨出画再入画都不变的 id
  • 语义类别与相机系下的自身运动方向
  • 不需要网格、材质、骨骼，也不需要预定义动画
交给生成先验（渲染器负责）
盒子里面发生的一切
  • 精确形状、纹理、材质、光照
  • 关节运动与局部形变——走路、举枪、倒地的具体姿态
  • 次级动态：布料、尘土、阴影、抛壳
  • 换句话说：盒子说「他在这、他朝那、他在动」，模型说「他长什么样、动作怎么走完」
我的读法

这套论证是干净的，但注意它有一个隐含前提：盒子能表达的状态变化，必须足够让生成模型猜对剩下的。 「人在跑」和「人倒地」之间，盒子能给的差别只有姿态（立方体躺倒）和 7 档方向里的 down。 对「开门 / 关门」「拿起 / 放下」「装弹」这类交互，一个盒子加一个类别标签能不能撑住？论文没有测，也没有讨论。 我怀疑真实答案是：语义标签字符串在偷偷承担很多工作——见 §04 末尾和存疑第 1 条。

03World Program

世界程序与引擎：账本长什么样

这一段是纯软件工程，没有任何模型。理解它最快的方式是把它当成一个只算规则、不算物理的迷你游戏引擎。

st = ( Et , At , Qt ; Rt ) Eq.4 E 持久实体及其 3D 位姿　A 语义与功能属性（hp、status、faction、库存…）　Q 实体间关系（敌对、归属）　R 可执行规则。 分号很讲究：R 和前三者是不同种类的东西，但它同样存在于状态里，也就是说规则本身可以在运行中被改写（论文原话：「entities, attributes, relations, and potentially the rule set」）。
st+1 = F( st , at ) Eq.5 每一步引擎做三件事：校验动作合法性 → 应用效果 → 结算被触发的事件。 注意第一步——动作可以被拒绝。这是纯生成式世界给不了的：prompt 一个非法动作，模型总会画点什么出来。

3.1初始化：检测器给几何，agent 给其余一切

给定首帧 I₀，一个现成的 3D 检测器先把可见实体和它们的 OBB 恢复出来，作为 E₀ 和持久 id 的来源。 剩下的——属性、关系、规则、事件触发器、胜负目标——由 agent 结合用户那句话写成程序， 通过 id 挂到检测出来的实体上，再交给引擎实例化成 s₀。

论文举的例子就是战斗场景：把检测到的角色分成敌我阵营、初始化血量和战斗状态、规定谁可以打谁、定义「射击」的伤害/死亡/目标更新效果。 作者的原话很到位：这不是在造一个有完整 3D 资产和底层仿真逻辑的常规游戏，而是编程一个轻量的「盒子世界」。

一个容易被读漏的设计

论文特意点出：世界状态里可以有完全不出现在观测里的变量（hp、库存、阵营），它们不进渲染，但会决定后续的状态转移。 这句话是整个「解耦」的价值所在——一个纯生成式世界，没有地方安放这种量。 你可以把 hp 写进 prompt，但那不是状态，那是描述。

04State Compiler

状态编译器：把账本压成三张像素对齐的图

这是全文技术含量最集中的一节，也是我认为最漂亮的一节。 编译器 P 做的事听起来平平无奇——「投影 + 光栅化」——但三张图的分工设计非常讲究， 尤其第三张，解决了一个所有相机可控视频模型都躲不掉的歧义。

Mctrlt+1 = P( st+1 , Ct+1 ) Eq.6 关键词是 without altering the underlying world state：编译器是只读的。 它从状态里挑出「必须被空间定位」的那部分，其余（hp、库存）原封不动留在账本里。

4.1三张图各管一件事

Mid · 身份图
「这块像素属于哪一个实例」

维护一个 K 个可学嵌入的 bank Eid={qidj}，每个持久实体分到一个 slot， 整段序列内固定，光栅化到它 OBB 的可见投影上。

训练时 slot 在每个样本内随机且互不重复地分配、样本之间重新随机—— 作者说这是为了防止某个 id 嵌入和特定类别/外观/视角绑死。这个细节很关键： slot 是「代词」不是「名字」，它只保证「前后这两块像素是同一个东西」，不携带任何外观信息。

Msem · 语义图
「这块像素是什么类别」

把账本里的类别标签 yi 过一个预训练文本编码器： qsemi = Etext(yi)，同样光栅化到可见投影上，背景填零。 多个框重叠时用深度感知光栅化保留可见的那个。

同类实体共享同一个语义表示，靠 id slot 区分个体。论文点明它的主要用途： 那些首帧里根本不存在、没有外观参考的实体——比如刚从画面外走进来的 NPC。

Mdir · 方向图
「它自己在往哪动」

取引擎维护的世界系速度，旋到目标相机坐标系，量化成 7 档： forward / backward / left / right / up / down / static，各有一个可学嵌入。

这是整节的点睛之笔。画面上一个框动了，可能是它在动，可能是相机在动，也可能两者都有。 因为方向是从世界速度算的而不是图像位移，静止物体在相机横摇时依然被标为 static， 于是渲染器能把「自身运动」和「相机带来的表观运动」分开——正好补上原生相机通路管不到的那一半。

Mctrlt+1 = Concat( Midt+1 , Msemt+1 , Mdirt+1 ) Eq.10 沿通道维拼接，编码到视频 latent 的空间分辨率后送进 ControlNet。 请数一下这里有几个通道组：三个。身份、语义、方向。没有一个叫 status。记住这一点。
⚠ 全文最大的一处「说了但没说清」：status 是怎么进到控制信号里的

标题里写着 state-augmented 3D OBB，Fig.1 里画着 status: active → down， 实验的头号指标是 State Accuracy 98%——衡量「死亡事件有没有被画面兑现」。 可是 §4.3 从头到尾给出的控制信号只有 Concat(Mid, Msem, Mdir)， 没有任何一路承载 hp / status。那 98% 是怎么来的？只可能是下面两条之一，而论文一条都没写：

  • 假设 A：语义标签被改写。死亡时把 yi 从 soldier 换成 dead soldier， 文本嵌入随之改变。问题：训练标签来自 SAM3，而 SAM3 的类别词表是 Qwen3-VL 从视频里发现的「离散可数物体类别」—— 这种词表大概率给不出「dead soldier」这种状态化类别，于是训练期根本没有对应监督。
  • 假设 B：纯靠 OBB 几何。倒地就是盒子躺平（extent 与 orientation 变化）+ 方向图给一个 down。 这条更可能是真的，因为它不需要额外通道，而且训练数据（三款游戏的战斗镜头）里「人躺着」的先验极强。 问题：如果是这样，那么所有「不改变几何的状态」都无法被渲染——中毒、上膛、护盾开启、门锁上了没有—— 而「hp 这类非视觉量也能影响渲染结果」正是论文自己在 §4.2 结尾许诺过的能力。

这不是吹毛求疵：它决定了这套接口的能力边界到底在哪。等代码放出来，这是我第一个要去读的文件。

06Long Horizon

长程：分块自回归 + 两种记忆

窗内双向去噪，跨窗因果传播。第一块从 I₀ 起步（历史填零、无空间记忆），之后每一块多吃两样东西。

I(n) = Gθ,φ,ψ( C(n) , Mctrl,(n) , H(n)temp , H(n)spa ) ,   n ≥ 2 Eq.14 两路记忆只由「生成当前块之前已有的观测」构成——这保证了跨块的因果性，也意味着一块里的错误会顺着记忆往下传。
Htemp · 时间历史
多尺度的近中远三档 + 一个永不过期的锚

近处 latent 投成更细的时空 token，越远越粗——在固定 token 预算下把有效时间窗撑长。 另外首帧 I₀ 的 latent 始终保留作为持久锚点。

训练时故意把历史弄脏：加噪、特征腐蚀、随机丢弃部分历史，让渲染器学会容忍不完美的自回归上下文。 推理时每块把自己的生成 latent 交给历史，形成因果 rollout。这是很实用的一招—— 训练用真实帧、推理用生成帧的分布差，靠人为退化去弥合。

Hspa · 几何对齐空间记忆
直接沿用 AlayaWorld 的机制

把已完成的 RGB 帧用估计深度和相机参数抬到世界空间；生成新块前检索相关历史观测、 重投影到目标视角，编码成空间 latent token 参与条件。记忆只从已完成的块更新。

解决的问题很具体：时间历史窗口有限，大幅相机运动、遮挡、回到走过的地方时， 近期上下文里已经没有那段内容了。

留意一个方向性

记忆是视觉的，账本是符号的，而且单向：生成的画面会进记忆，但永远不会反过来修改世界状态。 好处是状态绝不会被幻觉污染；代价是渲染失败没有任何反馈闭环—— 如果渲染器某一块没把一个实体画出来，引擎不知道，下一块照样按「他还在那」继续编译。 画面和账本一旦分叉，只能靠空间记忆自己纠回去。论文没有讨论这种分叉。

07Data Engine

数据引擎：从无标注视频里把监督挖出来

要训 ControlNet，就得有「视频 ↔ 三张控制图」的配对。野生视频里没有这种标注， 所以作者拼了一条五段式的自动管线。这条管线的精度，就是整套监督的天花板。

训练数据
三款游戏的无 HUD 实录

Cyberpunk 2077（第一人称）、Forza Horizon 6、GTA V（第三人称，多样视角）。 走上面那条管线产出配对数据。

论文没给：时长、clip 数、分辨率、帧率、过滤后保留比例。也没有讨论素材许可问题。

8.3基线是怎么被驱动的——这一条最影响可比性

两个基线都没有实例级状态接口，于是作者用换 prompt 来传达状态变化：

{environment description}. {action description}.        ← Eq.16
例：某个 NPC 被击杀时，把 action description 换成「让对应角色倒下」这类描述
⚠ 一个没被讨论的混淆：相机轨迹对齐了吗

Count Accuracy 的真值是「引擎维护的、当前视野内的存活角色数」——它依赖相机。 可是论文对基线的说法只有一句「retaining their native conditioning pathways」， 没有说是否把同一条目标相机轨迹喂给了基线，也没有报告任何一方的相机轨迹跟随误差。

如果基线的相机跑偏了，实体进出画面的时机就跟引擎账本对不上，于是它们会因为相机误差被记成状态错误。 而 PWM 这边，相机轨迹和投影框是同一条轨迹下构造的、天然自洽的。 这不是说 PWM 没有优势，而是说：40.75 → 94.00 这个差值里，有多少来自「状态解耦」、有多少来自「相机对齐」，这篇论文没法回答。

还有一个更小但同样实在的混淆：PWM 的主干是 LingBot-World-v1，基线之一是 LingBot-World-V2。 骨干不同，做不了 apples-to-apples。真正能隔离贡献的实验只有一个——在自己的主干上做消融——而这篇论文一个消融都没有。

8.4定性结果里真正有信息量的两张

Fig.5(b) · 大角度转身
转过去，三个人在那儿

相机大角度旋转（项目页写 −130°），揭示出三个首帧视野之外的角色。 这是「离屏持久化」最直观的证据，也是纯生成式模型最难做对的一类镜头。首帧取自训练未见的 GTA V 素材。

但要清醒：被持久化的是位置和身份，不是外观。id slot 训练时故意与外观解绑， 从未被观测过的实体只能靠语义嵌入 + 生成先验「编」一个长相出来。见存疑第 12 条。

Fig.5(e) · 897 帧
大量 NPC 陆续进场，不崩

单条自回归序列 897 帧，越到后面同屏实体越多，视觉与时间稳定性仍然「reasonable」。 项目页称约 30 秒，即 ≈30 fps 播放。

没有逐段的漂移曲线，没有与更短 rollout 的定量对比，没有生成耗时。 「不崩」目前只有几张抽帧作为证据。

另外三张：(a) 米诺陶场景（新外观/新环境泛化）、(c) 赛车（换游戏品类）、(d) 人与车混合渲染。 (a)(c)(d) 的首帧由 GPT Image 2 生成——意味着数据引擎那条管线（单目深度 + 3D 检测）也被用在了合成图上， 这本身是个值得关心的鲁棒性问题，论文没提。

09Open Questions

我的存疑清单

按「如果这条成立，会动摇论文多少结论」排的严重度。需要说明的是： 我认为这篇论文的方向和主要结论是成立的——把状态外置确实能拿到纯生成式方法拿不到的一致性。 下面这些质疑针对的是证据强度和边界描述，不是针对结论本身。另外，这是一份技术报告风格的 v1， 很多缺失可能只是还没写进来。

按严重度筛选：
D01高「state-augmented」的 state 到底走哪个通道进渲染器，全文没有交代▸
论文说了什么
Mctrlt+1 = Concat( Midt+1 , Msemt+1 , Mdirt+1 ) —— Eq.10 / Eq.11
问题

三路控制分别编码实例身份、类别语义、相机系运动方向。没有一路是 status / hp。 而全文的头号实验指标 State Accuracy 恰恰只衡量「死亡状态有没有被画出来」。 §4.2 还明确许诺过「hp 这类非视觉变量……可以影响后续的状态更新与渲染结果」。 渲染结果怎么被影响的，方法部分没有写。

两条可能的解释与各自的代价

A（语义标签改写）：死亡时把 yi 从 soldier 换成 dead soldier。 代价：训练标签的类别词表由 Qwen3-VL 从视频里发现「离散可数物体类别」再喂给 SAM3， 这种词表通常给不出状态化类别，训练期缺乏对应监督。而且如果成立， 意味着「可编程状态」在渲染这一端退化成了「实体级的文本提示」——那和作者批评的 prompt 控制只差一个粒度。

B（纯几何）：倒地 = OBB 躺平 + 方向图给 down。这条更可能是真的，也更自洽。 代价：所有不改变几何的状态一律无法渲染——中毒、上膛、护盾、门是否上锁、任务标记。 那么这套接口的表达力，其实就等于「盒子的姿态 + 一个类别词 + 七个方向」。

怎么验

看代码里 state compiler 的 semantic_label 是否随 status 改写； 或做一个只改 status、不改 OBB 姿态的对照序列，看渲染是否有任何变化。

D02高Count Accuracy 的真值依赖相机，而基线的相机是否对齐没有交代▸
机制

真值是「引擎维护的视野内存活角色数」。视野由目标相机决定。 PWM 的相机轨迹与投影框由同一条轨迹构造，天然自洽；两个基线只被告知 {environment}. {action}. 这样一句 prompt，论文只说「retaining their native conditioning pathways」。

后果

若基线相机跑偏，实体进出画面的时机与账本对不上，它们会因相机跟随误差被判成状态错误。 40.75 → 94.00 这 53 个百分点里，有多少来自「状态外置」，有多少来自「相机对齐」，这篇论文回答不了。

最小修补

报告三个方法各自的相机轨迹跟随误差（相对目标位姿的 ATE/RPE）， 或只在静态相机子集上再算一遍两个指标——Fig.4(a) 已经有静态相机设定，做这件事几乎是免费的。

D03高零消融：三张控制图、id slot bank、两种记忆，没有一项被单独验证▸

论文引入的可训练组件与设计选择至少有：identity 图（含 K 个可学 slot 与随机分配策略）、semantic 图（文本编码器嵌入）、 direction 图（世界速度→相机系→7 档量化）、多尺度时间历史（三档分辨率 + I₀ 锚点 + 训练期历史退化）、几何对齐空间记忆。 实验部分只有一张三行的对比表，没有任何一行是自己的变体。

最想看的三个消融，成本都很低： ① 去掉 Mdir（直接检验「相机–物体运动歧义」这个卖点）； ② 去掉 Mid（检验出画再入画的身份保持）； ③ 去掉空间记忆（检验 Fig.5(b) 那种大角度回望）。 没有它们，读者无法判断 94/98 里哪一部分是这篇论文的贡献、哪一部分本来就来自 LingBot 主干和 AlayaWorld 的记忆。

D04高最相关的三个对手一个都没比：StatePlay、MASS、Coarse-to-Real▸

§3.2 专门讨论了 StatePlay（联合预测观测与游戏状态变量）和 MASS（多人世界模型的权威类型化状态 + 学习式 Logic Engine）， 并准确指出了它们的共同弱点：状态本身由模型预测，因此转移误差会累积。§3.3 讨论了 Coarse-to-Real（粗 3D 代理 → 生成式渲染）， 它的渲染接口与本文几乎处在同一层。

但实验里一个都没有。比的是两个「压根没有显式状态接口」的通用交互式世界模型。 这就像用「有没有账本」去证明「我的账本更好」——命题为真，但没有回答真正的科学问题： 在都有显式状态的前提下，「规则驱动 + 确定性编译」相对「学习式状态转移」的收益有多大？

公允地说：MASS / StatePlay 未必有可用的开源实现，Coarse-to-Real 的任务设定也不同。但这一点应该写进 limitation，而不是不提。

D05中指标宽松到能被「死错人」完全绕过，而且缺一条 oracle 上限▸
宽松度

State Accuracy 只问「事件后 3 帧里有没有某个角色显得死了」，不问是谁、不问在哪。 §08 的显微镜里那条「死错人」——该死的还站着、旁边的倒下了——两个指标同时判过。 而实例级可寻址恰恰是这篇论文的核心卖点。

缺失的 oracle

Count Accuracy 94% 里，有多少是渲染器画漏/画多，有多少是 Qwen3.6-27B 判官自己数错？ VLM 在多目标计数上是有名的不稳。论文没有给判官的上限对照—— 只要把同一批判官问题喂给真实游戏视频或按 GT 状态渲染的视频，就能读出这个天花板。没有它，94% 无法解释。

还有一个定义盲区

「visible alive characters」里的 visible 到底怎么算：只做视锥剔除，还是也做遮挡剔除？ 半个身子出画算不算？被掩体挡到只剩一个头算不算？论文没定义，而这直接决定真值，也决定判官该怎么数。

D06中样本量小、无置信区间，小数点后两位是虚的▸

50 clips；Count Acc 的 400 帧来自这 50 个 clip（同 clip 内 8 帧高度相关，有效样本量远小于 400）； State Acc 的分母就是 50 次死亡事件——98.00% 即 49/50，8.00% 即 4/50。

用 Wilson 区间（§08 的 Fig.7 可以直接切换看）：保守口径下 94.00% 的 95% 区间约 [83.8, 97.9]， 98.00% 约 [89.5, 99.6]。结论方向完全站得住（与 40.75 / 32.00 / 8.00 的区间毫无重叠）， 但「94.00」「98.00」这种写法暗示的精度是不存在的。

另外 Imaging Quality 67.62 vs 67.46 这 0.16 分被写进「best across all four metrics」，实质上是平手。

D07中反复说「playable / 可玩」，却没有任何延迟或吞吐数字▸

摘要、引言、结论都在讲「users can create playable games」。但全文没有一个 FPS、没有一个 ms、没有 GPU 型号。 而这套推理路径并不轻：窗内双向去噪 + ControlNet 支路 + 多尺度时间历史 + 需要检索和重投影的空间记忆。

更值得玩味的是：同组的 AlayaRenderer-Flash（参考文献 [13]）专门解决实时生成式渲染的效率， 却没有被用作这里的主干；主干选的是 LingBot-World-v1。 在缺少延迟数据的情况下，「playable」目前只能理解为「交互语义上可玩」（有规则、有胜负、动作会被校验）， 而不是「时延上可玩」。这两件事在世界模型这个领域经常被混着说，读的时候要分开。

D08中Agent 那一环完全没有评估，而且它还兼任出题人▸

标题里的 Programmable 主要由「VLM coding agent 把自然语言翻成世界程序」这一环支撑。 但论文没有报告：程序生成的正确率、规则覆盖率、初始 3D 布局的解析成功率、 指令被误解时的失败模式、用户改一句话后规则改写的成功率。一个用户研究也没有。

更需要注意的是 CombatStateBench 的构造：初始布局由数据引擎从首帧重建， 然后「一个 AI agent 自主演化出一段简短的战斗场景，产出完整的盒子世界状态序列」， 再由一个自动校验器筛掉不满足一致性检查的序列。也就是说—— 出题的 agent、答题的系统、和被评估的表征，是同一套东西。 能通过校验器的序列，天然就是这套表征能干净表达的序列。

这不必然导致结论错误（毕竟基线在同样的序列上被评），但它意味着 CombatStateBench 不是一个中立的第三方基准， 而更接近「本方法的能力边界内的一致性自检」。

D09中训练标签与基准真值同源，且单目 3D 检测的误差从未被量化▸

训练数据的三张控制图，来自 ViPE（内参/位姿/metric depth）→ SAM3（实例与 track）→ WildDet3D（单目 3D OBB）这条链。 整套监督的精度上界就是这条链的精度，而论文没有报告任何一环的误差，也没有做敏感性分析 （比如：给 OBB 加多大的抖动会让渲染质量掉多少）。

同一条管线还被用来构造 CombatStateBench 的初始布局与「真值」状态。 于是 训练表征、推理表征、评测真值三者同源。这会系统性地让本方法显得更好： 任何被这条管线系统性漏掉或扭曲的东西，同时从训练集和测试集里消失了。

D10中「训练–推理错配」是全篇立论，却从头到尾没有被测量过▸

§2 用了两页论证：表征越细，Eq.1（测出来）和 Eq.2（造出来）之间的差距越大，所以要选中等粒度。 这是我认为本文最有价值的一段思辨。但它始终停留在思辨。

OBB 这一层的错配其实是实打实存在的：训练期的框来自检测器，带抖动、带尺度误差，但服从真实物理； 推理期的框来自程序，干净、平滑、可以完全违反物理（比如让一个人 0.2 秒内平移 5 米）。 这个分布差有多大、渲染器对它有多敏感，一个实验都没有。

最容易做的验证：拿真实视频的检测框 vs 程序生成的等价轨迹，各渲染一遍，比较质量与状态一致性； 或者给程序轨迹注入不同幅度的抖动，看哪一档最接近训练分布。

D11低identity slot bank 的 K 没给，实体数超过 K 怎么办也没说▸

Eq.7 定义了 K 个可学 identity 嵌入，但 K 是多少没写。 Fig.5(e) 明确展示「大量 NPC 陆续进场」的 897 帧序列——同屏实体数增长时， slot 用尽了怎么办（复用？环形分配？合并？），复用会不会造成身份串味，论文都没有交代。

另外训练策略是「每个样本内均匀随机分配互不重复的 slot」，这意味着 slot 承载的是纯粹的区分性。 那么当同屏实体数超过训练时见过的最大值，泛化行为是什么？也没说。

D12低「离屏持久化」持久化的是位置和身份，不是外观▸

这不算错误，而是一个容易被 Fig.5(b) 的演示带偏的边界。id slot 在训练时被刻意与类别/外观/视角解绑 （「preventing individual identity embeddings from becoming spuriously associated with a particular object category, appearance, or viewpoint」）， 所以它只保证「这两块像素是同一个东西」。

对于首帧从未出现过的实体，渲染器手上只有：一个类别文本嵌入 + 一个无语义的 slot + 一个盒子。 长相完全由生成先验编。论文自己也承认语义图「对缺少可靠外观参考的实体尤其有用」—— 换句话说，它编得合理，但不是「那个人」。如果你需要一个具名 NPC 在转身后长相一致，这套接口目前给不了。

D13低四个 VBench 质量指标对「少动」有系统性偏好▸

Subject Consistency、Background Consistency、Temporal Flickering 本质上都在测跨帧相似度—— 一个动得更少、更保守的视频天然得分更高。三个方法生成的内容本身不同（尤其基线的状态转移是靠换 prompt 触发的， 可能引发更剧烈的画面变化），因此这三项的差距不能直接读成画质更好。

要把这条排除掉，需要报告运动幅度（比如平均光流强度）作为协变量，或者用 VBench 的 Dynamic Degree 一起看。论文没有。

D14低渲染失败没有回流路径：画面和账本分叉了，系统不知道▸

数据流是严格单向的：状态 → 控制图 → 画面 → 记忆。画面永远不修改状态。 好处很明确（账本不会被幻觉污染，这正是相对 StatePlay 的优势）。 但反过来：如果渲染器某一块没把某个实体画出来，引擎完全不知情，下一块照旧按「他还在那」继续编译， 而空间记忆里存的是错误的那一帧。

Count Accuracy 94% 意味着大约每 16 帧就有 1 帧对不上账——这种分叉是实际发生的。 论文既没有测量分叉的持续时间，也没有讨论任何纠正机制（比如用检测器回读生成帧、做闭环校验）。

D15低若干小口径问题▸
  • VBench 版本：正文描述的 Imaging Quality / Subject Consistency / Background Consistency / Temporal Flickering 是 VBench-1.0 的指标名，引用挂的却是 VBench-2.0（参考文献 [24]）。
  • 方向档位顺序不一致：§4.3 写 forward, backward, left, right, static, up, down，§4.5 写 static, left, right, up, down, forward, backward。集合一致，只是不整齐。
  • 日期：论文页脚写 September 10, 2026，arXiv 时间戳是 9 Sep 2026。
  • 机构：只给了 △ = Alaya Lab；Jiacheng Lin、Yu-Lun Liu、Yung-Yu Chuang 三位没有任何机构标注。
  • 阈值缺失：SAM3 掩码的「可见面积不足」阈值、判 static 的位移阈值，都只说「a small threshold」。
  • 代码：GitHub 的 Release Roadmap 里 Inference code 与 Pretrained weights 两项均未勾选（2026-09-10 查）；项目页上的 Hugging Face 徽章指向的是 Daily Paper 页面，不是权重。
反过来说，我认为这篇站得住的地方
  • §2 的论证是真的好。「训练是测出来的、推理是造出来的」这个不对称，是选表征时最容易被忽略、又最要命的一条判据。即使你不同意 OBB 是最优解，这个思考框架也值得抄走。
  • Mdir 的设计是干净的正确。用世界速度而非图像位移定义方向，把相机–物体运动歧义在条件构造阶段就消掉，而不是指望模型学会区分。这是那种「一看就对」的设计。
  • 把 identity slot 训成「代词」而非「名字」，通过样本内随机、序列内固定的分配防止 slot 与外观绑死——这个训练细节很有品味。
  • 状态外置带来的能力是真实的：动作可以被拒绝，hp/库存这类非视觉量有地方安放，离屏实体不靠记忆而靠账本存在。这三件事纯生成式方法目前确实做不到。

推理设置：去噪步数 / CFG / 采样器未给无法比较速度与质量
推理延迟 / 吞吐未给「playable」这个词的成色全靠它（D07）
3D 检测器在推理端的具体型号只说 off-the-shelf§4.5 用的是 WildDet3D，§4.2 只写「现成的 3D 检测器」，是否同一个未明
掩码面积阈值 / static 位移阈值未给只说「insufficient」「small」，直接影响标注质量与 dir 分布
CombatStateBench 的自动校验器细则只有条目名它决定哪些序列进了基准，是 D08 那条循环性的关键（各项阈值全未给）
11Positioning

与本仓库的关联：它在这条线的哪一格

把「世界状态由谁维护、由谁推进」当作一根轴，这几年的工作能排得很整齐。 PWM 站在最右端——状态既不由模型表示，也不由模型推进。

如果你在维护这个列表，PWM 的几个字段大致是： Backbone bidir. diffusion（LingBot-World-v1 主干 + ControlNet）； Action 相机 + 实体级程序化动作（论文未定义按键映射）； FPS —（未报告）； Memory hybrid：时间历史（多尺度）+ 空间记忆（重建重投影，沿用 AlayaWorld）+ 外部符号状态； Open no（代码与权重均未发布）。 最后那一项——「外部符号状态」——是现有表格里还没有的一列，而这篇论文说明它值得单开一列。

C名词表

OBB（Oriented Bounding Box）
有朝向的三维包围盒。相对轴对齐盒（AABB）多了旋转，用固定的一小组参数（中心、尺寸、朝向）描述一个实体在世界系中占的空间。本文的核心接口。
state-augmented OBB
在几何 OBB 之上挂了持久身份、语义类别、动态状态和外观信息。但注意：进入渲染条件的只有身份、语义、方向三路，status 走哪条通道论文没写（D01）。
确定性状态编译器
把世界状态 + 目标相机变成像素对齐控制图的一段普通程序。不学习、不改状态、给定输入必得同一输出——正是这个「确定性」把训练与推理的接口对齐了。
生成式渲染（Generative Rendering）
用生成模型代替传统图形管线，从结构化场景条件合成照片级观测。谱系上从 G-buffer（最显式）一路到粗 3D 代理（最轻），本文落在偏轻的一端。
分块自回归（Chunk-Autoregressive）
窗内双向去噪、跨窗因果传播。兼顾块内质量和长程可扩展，代价是块边界需要额外的记忆机制来缝。
相机–物体运动歧义
画面上一个物体的位移，可能来自它自己动、相机动、或两者叠加。本文用「世界系速度 → 相机系 → 7 档量化」的方向图，在构造条件时就把这个歧义消掉。

D如果只记三句话

机制
状态外置到一个按显式规则推进的轻量引擎，用state-augmented 3D OBB 当唯一接口，经确定性编译器变成三张像素对齐控制图，喂给一个冻结的视频主干。
收益
动作可被拒绝；hp/阵营这类非视觉量有地方安放；离屏实体靠账本存在而不是靠记忆。这三件事纯生成式方法目前给不了。
代价与未知
动力学从「学出来」变成「你写的规则」；status 如何进入渲染未交代；零消融、最相关的对手全没比、「playable」无延迟数据。
