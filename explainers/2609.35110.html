Sol-H3 精读：33B 的 MiniMax-H3 从两分半压到几秒，这笔账怎么算

全称 Sol-H3: Recursive Self-Improvement for MiniMax-H3 Inference Acceleration on Sol-Engine across Cloud and Edge。这是一份推理加速的技术报告。算法上，先用 H3 以 4 步生成低分辨率草稿，再交给 LTX-2.5 在高分辨率上做 3 步精修，两者之间用一个学出来的「跨 VAE 潜变量翻译器」衔接。系统上，由 agent 驱动的 RSI 循环去搜通信量化、MXFP8、稀疏注意力和算子融合。另外还有 DGX Spark 的边缘部署，以及 Ref2VA 的参考 KV 缓存。

一句话结论。几个工程件是真的，也可以直接复用：AdaLN 预计算（结果精确，省 24 GB）、跨 VAE 潜变量适配器（比「解码再编码」快 202×）、「LoRA 合并进 BF16 会把 86–94% 的更新舍入掉」这条诊断、VAE tile 的全局批处理、QKV 打包通信。

标题里的两件事站不稳。第一，「RSI」在正文里没有被描述，也没有任何消融能把它的贡献从头条数字里分出来。第二，22–31× 这几个头条倍数主要来自换了生成合同：49→4 步的第三方蒸馏 LoRA、把低分辨率草稿交给另一个模型精修、用小自编码器做近似解码。论文在 §2.2 自己说过，这两类加速不应混在一起报。

更要紧的是三处核对结果：GB200 上两阶段的 6.852 s 不是 §3.1 描述的那条管线测出来的；表 1 的基线列与作者仓库里 B300 上 SGLang 的数字逐位相同；全文没有任何量化质量评估。

02背景：MiniMax-H3 为什么这么贵

H3 是一个 33.1B 的稠密单流 Transformer。它把文本、条件视频、音频和目标视频拼成一条序列：[ text | conditioning video | audio | target video ]，然后在 50 个块里对整条序列做全注意力。贵在三个地方。

① 序列长

5 s、1344×768 时整条序列是 38,247 个 token，其中目标视频 37,296 个，文本 537 个，音频 414 个。这个数我从论文里「4 卡上下文并行、每卡 9562 行」反推过一遍，也和代码注释、作者的 H3 DataCenter 页一致。

② 步数多

官方采样是 50 个调度点，也就是 49 次 DiT 前向。论文里 49 和 50 混用，仓库 README 解释了两者是一回事。

③ AdaLN 大得离谱

每个块都有一个 adaln_proj = Linear(2688 → 96,768)，约 2.6 亿参数，50 块合计 13.0B，占全模型的 39%。它的输入只有时间步嵌入，所以完全可以提前算好（见 §6）。

Stage 2 真的只是「补细节」吗：σ = 0.909 意味着什么

三条管线的 Stage 2 都用 LTX 官方的蒸馏精修调度：σ = 0.909 → 0.725 → 0.422 → 0。在 rectified flow 里，xσ = (1−σ)·x0 + σ·ε。σ = 0.909 时信号的幅度只剩 9.1%，逐元素的信噪比是 ((1−σ)/σ)² ≈ 0.010。换句话说，精修器拿到的输入里 99% 的能量是噪声。

布局为什么还能保住？因为噪声逐像素独立，而布局是低频信号。把 k×k 个像素平均一下，信号基本不变，噪声方差却降为 1/k²。所以分辨率越高、看得越粗，信噪比越高。这正是 SD3 以来「高分辨率要把时间步往高噪声偏移」的原因。下面的示意用一张合成图演示：左图是干净图，中图是加噪后的原分辨率，右图是 k×k 平均之后的样子（k 可选）。

04跨 VAE 潜变量适配器：本文最扎实的一块

H3 和 LTX 的 VAE 是各自独立训练的，潜空间互不相通。最直接的接法是把 H3 潜变量解码成像素，再用 LTX 的 VAE 编码回去，但这要多跑两个大网络。作者训练了一个 1.95 亿参数的卷积网络，直接做「H3 潜变量 → LTX 潜变量」的翻译。空间放大交给另一个现成的 H3 ×2 上采样器（第三方 LBH-123-AI），适配器只负责「同一像素分辨率下换坐标系」。

H3 视频 VAE

24 通道，空间压缩 16×。时间上按 17 帧一块独立编码，每块 5 个 token，锚点在块内第 0/4/8/12/16 帧，所以名义上是 4× 压缩，但块与块交界处的时间间隔不均匀。192 帧的片段得到 24×57×48×84（末尾按配置删掉 3 个 token）。

LTX-2.5 Conv 视频 VAE

128 通道，空间压缩 32×，时间上是因果的 8× 网格：第 0 个潜变量对应第 0 帧，第 k 个对应第 8k−7 到 8k 帧。输入补到 193 帧，得到 128×25×24×42。

第一步：按物理时间对齐，而不是按张量下标

05RSI 系统栈：通信、MXFP8、稀疏注意力、融合与 LoRA 精度、VAE 分片

先说「RSI」本身

标题叫 Recursive Self-Improvement，但正文对这个循环只写了一句：「搜索核融合、内存布局、集合通信布局和传输精度，测延迟，并检查数值一致性」。用的哪个 agent、迭代了多少轮、搜索空间多大、接受阈值是多少、拒绝了多少候选、人工介入了多少，一概没有。前作 Sol Engine（arXiv 2606.23743）的流程是「并行技能 agent + 集成 agent + 人工验收」，作者栏里写着 NVIDIA SANA Team, Codex, GPT-Image2。此外，被改进的是 H3 的运行时，不是 agent 自己，「递归自我改进」这个名字并不贴切。

论文 §2.3 还说，这个循环是 fail-closed 的：「被接受的改动保证是同基线、同硬件下 like-for-like 的缩减」。可实际被接受的改动里就有 MXFP8、INT8/FP8 传输、稀疏注意力，这些都会改变输出。仓库 README 自己测过：只开 MXFP8，输出与 BF16 相比 PSNR 就只剩 13.82 dB。

5.1 注意力通信：把三次 all-to-all 合成一次，再压成 8 bit

多卡时用的是 Ulysses 序列并行。注意力之前，要把「按序列切分、每卡持有全部头」换成「按头切分、每卡持有全部序列」，算完再换回来。基线每层要做 4 次集合通信（Q、K、V 各一次，输出一次）。在一个全分辨率的代表性 profile 里，每个去噪步有 94 ms 花在布局拷贝（42 ms）和通信（52 ms）上，而注意力计算本身是 341 ms。改动分三层：

  • 打包 QKV：三次输入交换合成一次，每层总共 2 次集合通信，总的 payload 不变。
  • stride-aware 内核：朴素的 PyTorch 写法（先 stack 再 permute().contiguous()）会把激活复制两遍，吞吐只有参考实现的 0.953×，反而变慢。新内核按原有 stride 直接读 Q/K/V，一遍写进交换缓冲区，结果与参考 permute 按位一致。
  • 量化传输（近似）：每个「token × 头」的记录按下图压缩。

5.2 MXFP8 GEMM：第 2–46 块的注意力和 FFN 线性层

5.3 Sol-Attn：用「均值 + τ 倍标准差」选块

5.4 算子融合，以及本文最有用的一个发现：LoRA 合并会「悄悄丢更新」

RSI 找到三组可融合的算子：① 残差加法 + 按索引的门控 + RMSNorm + 按索引的 scale/shift 调制；② QK 归一化 + 部分 RoPE；③ SwiGLU 的切分、SiLU 与乘法。项目页估计每张卡每次 DiT 前向能省下约 178 GB 的访存。纯布局变换按位一致，算术融合则可能因为中间精度和舍入不同而不再按位一致。

LoRA 部分值得细看。把 W + BA 合并进 BF16 权重，可以省掉 LoRA 的额外 GEMM。但少步蒸馏 LoRA 的更新量往往很小，小到加上去之后在 BF16 里又舍入回原值。作者在 8 步适配器的 6 个投影里统计到，86.1–94.4% 的非零更新合并后回到了原值。受控诊断（同一输入、第一步）的结果：

35.26%合并进 BF16 权重（FP32 计算）vs 原生分支的相对 RMSE
6.24%合并但权重保留 FP32
6.08%分支本身改为 FP32 计算（说明原生 BF16 分支本身也有约 6% 的误差）

作者的解法叫 consumer fusion：保留 base 和 LoRA 两条分支（同样的 3 个 GEMM、同样的归约顺序），只把 base + δ 的加法融合进下一个消费者内核，并在原来的位置显式舍入到 BF16。结果与原生分支逐字节一致（3 个 15 s 样本，4 卡上的每次评估），延迟比原生分支低 0.694 s（2.64%），但仍比合并权重慢 0.804 s（3.24%）。图 8 的例子很直观：同种子、同噪声，仅仅是合并方式不同，恐龙长相、女孩发型、蝴蝶爆发的时机就全变了，蝴蝶周围还出现网格状色块。

5.5 VAE 解码：196 个 tile 怎么分给 8 张卡

上下文并行只切了 Transformer，VAE 解码默认每张卡都完整解一遍。5 s、1344×768、124 帧时，H3 解码器要处理 7 个时间片段，每片 28 个空间 tile，共 196 个。三步优化：① 把 tile 分到 8 卡，7.55 → 1.16 s；② 每卡同一片段的 4 个 tile 合成一个 batch，→ 0.602 s（1.93×）；③ 编译，→ 0.359 s（对分片基线 3.23×），峰值显存 18.8 → 15.6 GB，但与 eager 结果不再按位一致（最大绝对误差 0.021）。第四步「全局 tile 批处理」把 7 个片段的 tile 放在一起分配，填充槽从 28 个降到 4 个，只调用一次解码与 gather。这一步论文没有给延迟，只给了数值偏差：最大绝对误差 0.0137，PSNR 75.75 dB。

09存疑清单（18 条）

排序按「对结论的影响」而不是「错误的大小」。每条都附了论文原文和对照证据的出处。凡是涉及仓库和项目页的，核对的都是论文脚注引用的那个 commit（51b14fd）和 page 分支里的页面源码。

H1GB200 上 22.2× / 27.7× 的两阶段结果，不是 §3.1 描述的那条管线测出来的高

§3.1 描述的是：672×384、FastH3 VSA DataFree LoRA、H3 ×2 上采样器 + 学习型适配器，并声称「完全消除 VAE 解码再编码」。这与 Spark 的配置一致。§6.1 的 GB200 数字（6.852 s / 14.931 s）实际对应项目页和仓库 super_acceleration/ 的那条管线，差别有六处：

  • Stage 1 在 896×512 下运行，任务是 FL2VA 首帧条件，而非纯文本；
  • LoRA 是 LightX2V 4step_v0.1_544p，启动时合并，scale 0.0625；
  • 交接走像素：TAEH3 解码 → 缩到 672×384 → LTX 原版视频 VAE 编码 → 官方 ×2 潜变量上采样；
  • Stage 2 额外拿到 1344×768 首帧，作为硬条件；
  • 最终用 TAEHV 近似解码；
  • 适配器没有参与。

"Stage 1 obtains 124 decoded 896x512 frames from TAEH3, retains the first 121, resizes them on CUDA to 672x384 … Encode the direct 672x384/121-frame video with the original LTX-2.5 Video VAE input encoder."super_acceleration/STAGE2_CONTRACT.md

"Stage 2 retains the original LTX-2.5 Video VAE encoder because the Refiner was trained on its latent distribution."项目页 H3-Super-Acceleration

影响：论文把两套配方的「设计」和「数字」拼在了一起。读者会以为 22.2× 里包含了适配器的功劳，而实际起作用的是 TAE。

H2「单张 GB200 端到端 6.852 s」是两段分别测量后相加；仓库的正式测量每请求用 2 张卡，并明确不声明加速比高

论文原文是「measured on a single NVIDIA GB200 … end-to-end latency of 6.852 s, comprising 4.173 s for Stage 1 and 2.679 s for Stage 2」。项目页的计时说明是「Sol-Super combines separately measured Stage 1 blocks of 4.1728 and 9.8204 seconds … with the latest Stage 2 means from 10 hot complete-service requests」。仓库的正式测量（job 6304303）是 Stage 1 一张 GB200、Stage 2 另一张 GB200，20 次热请求的中位数为 6.7605 s，结论写的是：

"There is no matched same-profile end-to-end baseline, so this directory makes no speedup claim. A perceptual quality gate was not run, so successful media/telemetry validation must not be described as a quality pass."super_acceleration/README.md

引言里的「6.23 s，22.2×」也错配了：6.23 s 是图 5 不含 mux 的口径，对应 Diffusers 167.8 s 的 27.0×；22.2× 对应的是 6.852 s 与 SGLang 152.3 s。项目页上那组「每卡每天 12.6K 条、毛利 97.4%」的吞吐估算，同样是按一卡一请求算的。

H3表 1 标 GB200，但 Base H3 的 9 个数与仓库 README 里 B300 上 SGLang 的数字逐位相同高

129.898 / 376.942 / 746.885、35.328 / 100.440 / 194.930、18.250 / 50.660 / 99.513：九个数完全一致。README 写明「measured on NVIDIA B300 SXM6 AC GPUs」。项目页标题是「8× NVIDIA B300」，而论文参考文献 [79] 写成了「8× NVIDIA GB200」。作者的 H3 项目页在 8×GB200 上测的 SGLang 是 19.300 s。README 还写着「Kernel validation for this PR is limited to SM103 B300」（GB200 是 SM100，BENCHMARK_REFERENCE 里记为 compute capability 10.0）。

影响：要么是跨硬件比较（GB200 上的 Sol-H3 对 B300 上的基线），要么是表题写错。无论哪种，表 1 都不是「同硬件、同协议」的比较。论文 §2.3 自己要求的恰恰是「same baseline on the same hardware」。

H4头条倍数主要来自「换了生成合同」，这违反了论文 §2.2 自己立的规矩；RSI 的贡献无法从中分离高

"evaluating a different generation contract is not equivalent to accelerating a fixed one."论文 §2.2

  • 表 1 的 12.7–17.0× 里，49→4 次前向（第三方 FastH3 LoRA）就占了 12.25×，剩下的只有 1.04–1.39×（§8.1）。
  • 两阶段：只看算法，DiT 的 FLOPs 就少了约 23–26×（我的估算，§8.3），与实测 22.2× 同量级。
  • 全文唯一「算法不变、只换实现」的对比在项目页上（16.32 → 6.226 s，2.62×），其中 95% 的节省来自把完整 VAE 换成 TAE，属于近似解码，而且论文里没有出现。

没有一张「同 LoRA、同分辨率、逐项加上 RSI 组件」的消融表。标题叫「Recursive Self-Improvement for … Inference Acceleration」，但 RSI 对头条数字贡献了多少，读者无从知道。

H5没有任何量化质量评估；仅有的定性例子是首帧条件任务；仓库自测的 MXFP8 偏差未报高
  • 表 1 配置、两阶段、Spark、5090：没有 VBench、FVD、人评，也没有音频或口型同步指标。
  • §6.4 做了 3,000 次成对比较（人评子集 + VLM「Astra」），却一个胜率都没报，只列了「我们偏好」的适配器名字。
  • 图 6 的三个例子在仓库资产里是 FL2VA 首帧条件的对白任务（prompt 开头就是「Use the supplied image as the exact opening frame」）。其首帧元数据写着 "derivation": "first_decoded_frame_of_existing_…_benchmark_video"、"source_setting": "minimax-h3-bf16-50step-5s"。如果字段含义如其名，那么加速版与 50 步基线共享首帧，「保持场景结构与身份」几乎是自动成立的。
  • 仓库 README：只开 MXFP8，输出与 BF16 相比 PSNR 13.82 dB、SSIM 0.540。作者的 H3 页：即便是 50 步的 Sol-Engine「保质量」配置，LPIPS 也有 0.21。

图 8 本身就说明，任何数值改动都会让同种子下的样本面目全非，所以只能做分布层面的质量评估。这恰恰是本文缺的。

M6「精度保持的 LoRA 融合」没有进入任何头条配置，而头条配置正是论文诊断出有问题的「合并」中

表 1 写的是「merged four-step LoRA」。GB200 Stage 1 是「LightX2V four-step LoRA merged at startup」。Spark 是 "W8A8_FP8_after_BF16_LoRA_merge"。运行时默认 --lora-mode merged，而 fused 模式要求 --compute-quant none（「Quantized linear compute is not supported in branch modes」），与 MXFP8 互斥。论文自己的诊断是「BF16 合并吃掉 86–94% 的更新、首步相对 RMSE 35%」，这正好落在它的所有头条配置上。「合并后再量化到 FP8/MXFP8」的误差更大（见 §5.4 实验室），却完全没有量化。

M7§3.4 的稀疏注意力把 LTX 精修器和单阶段 H3 两套策略写成了一套，并漏掉了近似修正；没有给出任何数字中

「三个精修步 τ = 1/1.25/1.5」来自 LTX 精修器，该精修器只有第 0 层稠密。「前两层稠密」和「整段前缀当 sink」来自 H3 运行时，那里 τ 恒为 1.0。LTX 没有 packed 前缀。Spark 的 Ref2VA Stage-1 Sol 写着「neither H3 reference-image tokens nor Qwen visual tokens are sinks」，与论文「protection covers the entire prefix」相反。Sol-Attn 的核心是对未选块做零阶近似，论文只写了「只算超过阈值的块」。另外，没有稀疏率、速度或质量的数字。

M8Stage 2 从 σ = 0.909 开始（信号只剩 9%），远不止「补细节」；音画来自两个模型，没有同步指标；通用 prompt 没有消融中

论文没写 Stage 2 的 σ 调度。代码里是 0.909 → 0.725 → 0.422 → 0。最终音轨是 H3 原音，LTX 联合去噪出来的音频被丢弃，而画面（含嘴型）由 LTX 重画。在 Spark 上，这一步的文本条件还是一句与内容无关的通用 prompt。论文说「Stage 2 does not require per-sample text conditioning」，却没有做一个「用户 prompt vs 通用 prompt」的对比。云端版本其实仍然每个请求都跑 Gemma。

M9适配器：训练用真实视频的编码，部署时输入的却是放大后的生成草稿；质量只测到 Stage 2 之前；测速形状和硬件都不是部署时的中

训练对是「同一段真实视频在 1344×768 下分别用两个 VAE 编码」。推理时输入的是 672×384 生成草稿，经第三方 ×2 上采样器放大后的潜变量，两者分布不同。30.6 dB 衡量的是「与 LTX 自身重建是否一致」，接入管线后的最终视频没有评估，也没和完整 VAE 往返、TAE 往返比过质量。表 4 用的是早期 checkpoint、H100、192 帧。

M10Spark 的「31×」基线（≈1740.81 s）无处可查；项目页自己的对比是 6.7×中

仓库和三个项目页里都找不到 1740.81 这个数，论文也只写了「roughly」。Spark 项目页的对比是：4 步 LoRA 基线 374 s → 56 s，6.7×；4 步 LoRA + 量化 153 s → 2.7×。所以 31× 里大部分来自蒸馏 LoRA，以及避免了 49 步全分辨率下的 CPU offload。摘要里的「up to 30×」就来自这里。

M11RSI 循环没有被描述；「fail-closed：接受的改动保证 like-for-like」与实际被接受的有损模式矛盾中

缺的信息包括：agent 是谁、迭代多少轮、搜索空间多大、数值一致性阈值是多少、拒绝了多少候选、人工介入了多少。前作 Sol Engine 的作者栏里有 Codex，作者的 H3 页写着「3.95× in 4.5 hours of optimization」（50 步设置），这些都没有在本文出现。§2.3 说被接受的改动「guaranteed to be a like-for-like reduction」，可 MXFP8、INT8/FP8 传输、稀疏注意力都被接受了，而且都会改变输出。「递归自我改进」一词也不准确，agent 改进的不是它自己。

M12参考 KV 缓存的理由不完整：在全自注意力下，参考 token 的深层 K/V 依赖带噪的目标 token中

论文只讨论了时间步嵌入带来的漂移。在第一步缓存，等于把参考表示冻结在「目标还是纯噪声」时的上下文里。证据只有 3 个 V2V 编辑的定性例子。加速比本身与二次代价模型吻合（§7），问题在于「近似到底有多大」没有被量化。

M13基线与计时口径五花八门中

同一个「5 s、1344×768、单卡」工作负载，出现了 129.898 s（表 1，实为 B300 上的 SGLang）、152.3 s（SGLang）、167.8 s（Diffusers）三个基线，且都没有说明测量协议。计时口径也不同：表 1 不含 MP4 编码；Spark 的 56.17 s 含 MP4 封装与混音（1.3%）和请求开销（0.9%）；GB200 的 6.852 s 含 Stage-2 服务里的 mux，6.226 s 则不含。项目页说基线是「author-supplied warm end-to-end measurements」。

L14AdaLN 预计算「消除了严重的带宽瓶颈」说重了；它也不在 Spark 那 17.9% 的内存节省里低

每步 26 GB 在约 8 TB/s 的 HBM 上约 3.3 ms，占 49 步基线不到 0.2%。在 Spark 上约 95 ms/步，4 步约 0.4 s。真正的收益是 24 GB 内存。Spark 的 142.4 → 116.9 GiB 两根柱子都已是 FP8 H3，节省来自拿掉层间 VAE 和 Gemma/connector。

E4M3 的最小正规数是 2−6，其下是步长 2−9 的次正规数。幅值在 10−2 附近的注意力输出，量化相对误差可达约 10%。论文只写了「approximate」。

10可取之处、对世界模型的启示、最值钱的补充实验

做对了的
  • LoRA 合并的舍入诊断：先统计每个投影的 round-back 比例，再把「权重存储精度」和「GEMM 精度」分开测（35.26% / 6.24% / 6.08%），配上图 8 那种「同种子、仅合并方式不同」的受控演示。所有部署蒸馏 LoRA 的人都应该照做一遍。
  • AdaLN 预计算：刻意逐 (block, step) 跑 GEMM 以保证按位一致，省 24 GB，不需要任何质量门槛。
  • 适配器的工程细节：按物理时间对齐、无参数打包（每个源 token 恰好保留一次）、岭回归初始化的冻结跳连、解码器感知损失、held-out 256 段加配对 bootstrap 置信区间。参数量我按代码复算完全吻合。
  • 通信与 VAE 的小工程：QKV 打包后一遍写入，并记下了朴素写法反而慢 4.7% 的负结果；196 个 tile 做全局批处理，填充从 28 个降到 4 个。
  • 仓库文档比论文诚实：「no speedup claim」「quality gate was not run」「not a runtime-only speedup」「13.82 dB」这些话都写在仓库里，可惜没进论文。
对交互式视频世界模型的启示
  • 草稿 + 精修：精修器从 σ ≈ 0.9 开始时是在重新生成，逐块流式场景下的跨块一致性和动作响应都要单独评估。流式还需要因果的精修器，LTX 是双向的。
  • 跨 VAE 翻译器：想把世界模型的潜变量接到另一个解码器或精修器（参见本仓库的 renderer 候选文档），可以照搬「物理时间对齐 + 打包 + 解码器感知损失」这一套。但要在生成分布上训练和评估，不能只用真实视频的编码。
  • LoRA 合并：Self-Forcing / DMD 类的少步 LoRA 合并进 BF16 前，先统计一下 round-back 比例；上了 FP8 更要统计。
  • AdaLN 预计算：只对每块都带大 AdaLN 的架构才值（H3 占 39%）。Wan 系用的是共享的小投影，收益很小。
  • 上下文 KV 缓存：因果世界模型里天然成立；双向模型里缓存条件 token 是一种近似。
  • 测速体检清单：分段分别测完再相加、跨硬件的基线、换了合同的倍数、把 TAE 当作解码器，在世界模型的 FPS 报告里同样常见。
最值钱的补充实验（按性价比排）
  1. 同合同消融：固定同一个 4 步 LoRA、同一分辨率、同一台 GB200，逐项加上布局融合 → 算术融合 → 通信量化 → MXFP8 → Sol-Attn → VAE 优化，报告每一步的端到端延迟和质量。这张表能直接回答「RSI 值多少」。
  2. 两阶段 vs 单阶段 4 步全分辨率：比较质量（VBench + 人评 + 口型同步 LSE-C/D + 音质），并把 §6.4 已经跑完的 3,000 次比较的胜率报出来。
  3. 在同一台 GB200 上、用同一协议重测基线（SGLang 与 Diffusers 都测），替换表 1 的基线列。
  4. 适配器：在「上采样后的生成草稿」上评估；比较三种交接（适配器 / TAE 往返 / 完整 VAE 往返）在 Stage 2 之后的最终质量；扫描 Stage 2 的起始 σ（0.909 / 0.8 / 0.7），看身份保持与细节之间的取舍。
  5. merged vs fused：在头条配置下对比质量，并统计「BF16 合并 → MXFP8」之后的 round-back 比例。
  6. 参考 KV 缓存：量化近似误差，比如每隔 k 步刷新一次缓存，或让参考 token 只注意参考 token 的变体。
