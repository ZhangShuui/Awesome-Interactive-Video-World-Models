Incantation

把自然语言当作多实体视频世界模型的动作接口

现有交互式世界模型的动作，要么绑在引擎的动画 ID 上，要么绑在键鼠信号上，要么只是一句整场景字幕。 这三种接口在设计时就把动作语义焊死在了「某个实体 × 某个引擎」上。Incantation 的主张是：换掉接口本身。 它给每个实体一个语法上互相隔离的自然语言槽位，粒度精确到 0.25 秒一个 latent 帧， 于是同一个动作短语可以从它的原生角色迁移到另一个角色，也可以描述训练词表里根本不存在的动作 —— 这是任何离散索引接口在结构上做不到的。

00One picture

一图看懂：四种动作接口，只有一种同时满足两个必要条件

论文的整个论证建立在一个很朴素的框架上：一个能用的多实体动作接口，必须同时具备 开放词表语义（能表达训练词表之外的动作，且语义能在实体之间共享）和 逐实体可寻址（能分别对场景里的每个实体下达指令）。把已有工作放进这个二维坐标里，四个象限刚好各占一个。

TL;DR三句话版本

  1. 接口：在 Wan 2.2 TI2V-5B 上做微调，每 0.25 s（一个 VAE latent 帧）喂一条结构化 prompt， 形如 person_1 performs X. boss_1 performs Y.，槽位数量可增可减而不动任何架构。
  2. 架构：历史帧之间保留双向自注意力（不破坏 Wan 的预训练先验）， 文本 cross-attention 只作用在当前这一个含噪目标帧上（防止当前动作标签污染已提交的历史）。 位置编码用「sink 钉在 0 ＋ 局部相对位置 clamp 到上限 C」保证永不 OOD。
  3. 系统：ODE 初始化把双向教师对齐成因果学生，再用 Self-Forcing 蒸到 2 步； KV cache 用滑动窗口 ＋ 缓存未旋转的 K、查询时现场旋转，于是显存有界、位置永远在分布内， 2 小时 rollout 的 FVD 不漂。
01The bottleneck

被结构性忽略的场景：一个共享镜头，两个各自可控的实体

论文反复强调的战场叫 single-viewpoint multi-entity：一台摄像机，画面里同时有两个及以上独立可控的实体。 RPG 的 Boss 战、格斗游戏的 PvP 都是这个形态，而它恰好是现有交互式世界模型覆盖最薄的一块。

为什么薄？因为绝大多数系统把控制信号绑给唯一的「玩家」，画面里其余一切都是被动布景（GameNGen、Genie 系列、Oasis、Matrix-Game、MineWorld、WorldPlay）。 少数尝试多实体的工作，则各自绕开了这个形态的核心难点：

  • Solaris 能同步多人 Minecraft 视频，但输出的是每个玩家各自的第一人称流，没有共享镜头下的联合动力学；
  • COMBAT 在共享视角里渲染一个会反应的《铁拳 3》对手，但对手的策略没有任何可指令化接口；
  • MultiGen 靠外部记忆做可编辑的多人 rollout，ShareVerse 在 CARLA 上耦合四个 agent 视角，LiveWorld 关心视野外的持久性 —— 都不提供逐实体的语义指令。

作者由此把矛头指向接口而不是模型容量。他们列了三类现存接口各自的失效模式，并推出两条必要条件： 开放词表语义（让动作概念可以在实体之间共享）与 逐实体可寻址（让每个实体能被独立、同时地驱动）。 这两条正是 §00 那张图的两根坐标轴。

02Prompt formulation

接口本体：一条 prompt，每个实体一个语法隔离的槽

整篇论文的「接口」，落到实处就是一个字符串模板。它简单到有点反高潮，但两个性质是设计出来的，不是顺手写的。

Player performs [ACTION_P]. Boss performs [ACTION_B].
论文模板
并行性：两个槽在同一条 prompt 里、对齐到同一个 0.25 s 时间窗，模型被迫在这一帧内联合推理两个实体的交互动力学。
隔离性：语法上互不干扰，于是每个实体保留独立的控制通路。
可扩展：加一个实体就加一个句子，减一个就删一句 —— 不需要改动任何网络结构。论文正是靠这一点，用只训过两实体的模型直接跑出了三实体控制（Figure 1-ii）。

02.1粒度：一个「帧」到底是多久

论文全文的「frame」默认指 VAE 压缩后的 latent 帧，1 个 latent 帧 = 4 个像素帧；输出 16 FPS，所以 1 latent 帧 = 0.25 s，也就是每秒切换 4 次动作 prompt。而 FPS 一律指端到端的像素帧吞吐。这三者在读数字时极易混淆，作者在正文里专门用粗体做了声明。

开源代码里这件事是硬编码的常量，而且模板里的实体名是 person_1 / boss_1（论文正文写的是 Player / Boss，是同一件事的不同措辞）：

inference.py · class PromptGenerator（节选，原样）
  1. TIME_STEP = 0.25 # 每条 prompt 覆盖 0.25 秒 → 4 prompts/s
  2. DURATION_MAP = {"Standing": 1.00, "Move forward": 0.75, ...,
  3.   "Jump and mid-air slam": 4.50, "Heavy overhead slash": 5.00, ...}
  4. # 把「动作 + 时长」展开成逐 latent 帧的时间轴
  5. def _steps(self, duration): return max(1, int(round(duration / 0.25)))
  6. # 两条时间轴独立展开，短的那条用最后一个动作补齐
  7. max_len = max(len(p_tl), len(b_tl))
  8. p_tl += [p_tl[-1]] * (max_len - len(p_tl))
  9. return [f"person_1 performs {p}. boss_1 performs {b}." for p, b in zip(p_tl, b_tl)]
注意第 6–8 行：玩家和 Boss 的动作脚本长度可以完全不同，短的一方会保持最后一个动作直到另一方结束 —— 而不是补 Standing。这在写脚本时是个容易踩的坑。
为什么「语言」不只是换个说法

这里值得停一下。把 Action #17 换成 "Double light blade throw"，看起来只是把索引换成了字符串。 但索引的语义在投影矩阵的一行里，只有训练时和某个实体共现才有意义；而字符串的语义在预训练文本编码器里， light、blade、throw 这些子词单元早就在海量语境中被组合过。 于是「让从未做过这个动作的 Crucible Knight 扔出光刃」这件事，对索引接口是查无此项，对语言接口只是一次没见过的词组组合。 论文第 4 节的三条实验轴，本质上就是在把这句话拆成可证伪的形式。

03Context & attention

核心设计：历史保持双向，文本只碰当前这一帧

有了接口还不够。要让「一句 0.25 s 的话」变成「这一帧确实做了这个动作」， 必须回答两个问题：目标帧能看到多少上下文，以及文本被允许影响哪些 token。论文对这两件事都给了明确的、可消融的答案。

03.1上下文装配：Sink + Recent + Noisy = 9 个 latent token

训练时每一步只针对一帧 t 做去噪，喂给模型的窗口固定由三部分组成：

Ks = 1Sink 帧：整段 episode 的第一帧，永久保留，锚定竞技场几何与角色外观（沿用 StreamingLLM 的 attention-sink 思路）
Kr = 7Recent 帧：紧邻 t 的 7 个干净 latent，覆盖 1.75 s 游戏时间
Kn = 1Noisy 目标：正在被去噪的第 t 帧

03.2被规避的两个失效模式

① 预训练先验被毁

Bidirectional → Causal

Wan 2.2 是用全双向注意力预训练的，权重里编码的是对称的共现统计。直接扣上全局因果掩码等于丢掉这批先验，需要昂贵的重新适配。

② 时间维度的交叉污染

a_t → history keys

动作提示 at 只描述 t 时刻。若允许它 cross-attend 到历史帧，就会反向篡改已提交的过去，在相邻帧上留下「动作回声」。

03.32×2 消融：把两条约束各自拆开看

论文用一个 2×2 因子实验把这两条设计各自的贡献隔离开：横轴是文本 cross-attention 的作用范围，纵轴是历史自注意力的类型。 四个变体都从同一个 Wan 2.2 TI2V-5B 起训，超参完全一致（batch 64，lr 2×10⁻⁵，256×448），每 5k 步在留出集上按轨迹条件协议测 FVD，取最优检查点。

我的读法

论文对「因果 + 全文本」为何崩到 FVD > 1100 只给了一句解释（把 at 注入到已提交的因果历史键里，用未来动作信息污染了它们），没有做进一步的机理隔离。 我倾向于这样理解：因果历史的全部价值在于「第 i 个 token 不知道 t > i 的事」这条不变量。 一旦当前帧的动作标签被写进历史键，训练时历史里就带着「接下来要发生什么」，而 rollout 时不带 —— 训练与推理的分布直接错位，误差在自回归里被放大。 双向历史本来就允许窗口内互看，所以同样的注入不制造新的违约，这也解释了为什么 197.1 反而略优于 201.9。但这是我的推测，论文没有验证。

03.4教师与学生的掩码并不相同 —— 这一点容易读错

上面这套「双向历史」是 Stage 1 教师的设计。而流式推理要求 KV 一次写入、永不回改，这在结构上就等于严格因果： 历史帧不可能再回头看新帧。所以 Stage 2 学生是块因果（blockwise causal）的，两者的注意力掩码存在真实的落差 —— §05 的 ODE 初始化正是为了抹平它。

开源仓库放出来的是学生，所以你在 modules/causal_model.py 里看到的两个掩码构造函数都是因果的：

modules/causal_model.py · 两个训练期掩码（学生侧）
  1. # ① 块因果掩码：可选滑动窗口，且窗口之外永远保留 sink 帧
  2. def attention_mask(b, h, q_idx, kv_idx):
  3.   in_sink   = (kv_idx < frame_seqlen) # 第 0 帧，永远可见
  4.   in_recent = (kv_idx >= window_starts[q_idx]) & (kv_idx < ends[q_idx])
  5.   return in_sink | in_recent | (q_idx == kv_idx)
  6. # ws_frame = max(1, fi - window_size)：训练时的可见范围与推理 KV 窗口对齐
  7. # ② teacher-forcing 掩码：干净上下文 ‖ 含噪帧 拼成 2× 长序列
  8. clean_mask = (q_idx < clean_ends) & (kv_idx < context_ends[q_idx])
  9. noise_mask = (q_idx >= clean_ends) & (自身噪声块 | 之前的干净块)
  10. # ③ 文本只作用在含噪帧上 —— 训练与推理走同一行代码
  11. cross_attn_mask = (t > 0).float() # t == 0 的干净帧拿不到任何文本
第 11 行是 §03 那条设计在代码里的唯一落点，而且训练（_forward_train）和推理（_forward_inference）用的是同一个表达式 —— 这保证了「写进 KV cache 的干净帧从未见过文本」，我们在 §07 会看到它为什么关键。
04Bounded RoPE

位置编码：两个互相独立的「界」，把长时程从根上封死

自回归视频生成跑久了会崩，很多时候不是模型忘了内容，而是 RoPE 的位置索引跑出了训练时见过的范围。 论文把这件事称作 RoPE OOD，并且给了一个我认为相当干净的解法：两个界，各管一件事。

Kr · 滑动窗口大小

how many frames the KV cache holds

管住每步的计算量与显存。窗口一定，目标帧与任一 recent 帧的相对距离天然被夹在 [1, Kr] 里。

C · 位置上限（cap ≥ Kr）

largest local RoPE index any token can get

管住暴露给模型的位置范围。设成「推理时用到的每一个位置在训练时都出现过」，主要约束的是目标帧到 sink 帧那段会无限增长的距离。

位置的分配规则很简单：sink 帧永久钉在位置 0；含噪目标帧拿 min(pt, C)； Kr 个 recent 帧占据紧邻目标之前的连续位置。写成公式就是论文的式 (2)：

plocali = clamp(pabsi − δ, 0, C),　δ = max(0, pabst − C)
式 (2)
δ 是把整条时间轴往回平移的偏移量：当绝对帧号超过 C 之后，整个窗口整体平移，使目标帧永远停在位置 C。 sink 帧因为 clamp 的下界 0 而被自动钉住 —— 它的 pabs = 0，减去任何正的 δ 都会被夹回 0。这是一行公式里藏的两个机制。
05Stage 2 · distillation

从 50 步双向教师到 2 步因果学生：先对齐掩码，再压步数

Stage 1 的教师每帧要 50 步去噪、并且对整段可见上下文做双向注意力，单帧 12,058.7 ms —— 离「能玩」差了两个数量级。 Stage 2 要同时解决两个耦合的瓶颈：每帧计算量和每帧显存。论文把前者拆成了两步，顺序不能颠倒。

𝓛ODE = 𝔼τ, v₀, ε [ ‖ fθ(vτ ; causal) − fteacher(vτ ; bidir) ‖22 ]
式 (1)
学生用教师的权重初始化，然后在同一个噪声水平 τ 上，逼近教师预测的速度场。 注意这不是在压缩步数（那是下一步 Self-Forcing 的事），而只是在换一副注意力掩码的前提下把函数值对回去。作者报告 1,000 步内即可收敛。

Self-Forcing 的作用则是另一件事：训练时让学生以自己前面生成的帧为条件，而不是以真值帧为条件。 这直接消除了自回归视频扩散里典型的 train/test 落差（曝光偏差），把推理压到 2 步之后仍能稳住。 有意思的是，蒸馏后的学生 FVD 反而比教师更好（Elden Ring 138.6 vs 206.2；KOF 162.9 vs 170.1）， 这在少步蒸馏里并不罕见 —— 少步采样往往落在分布的高密度区，代价是多样性。论文没有报告多样性指标，这一点后面会再提。

06RoPE-decoupled cache

让滑窗真正能用的那一步：缓存未旋转的 K

这是我认为全文工程含量最高的一段，而且它的必要性完全来自 §04 的那个 clamp。

一旦位置变成局部相对的，它就是时间相关的：每淘汰一帧，活下来的键都要被重新指派一个新的局部位置。 而常规 KV cache 缓存的是已经旋转过的 K —— 它们的相位被锁死在写入时刻的旧索引上，和当前 query 的相位对不上，表现为生成视频的时间闪烁。

论文的做法是把两件事解耦：缓存旋转前的原始 K，查询时用当前最新的局部位置现场旋转。

Attn(qt, ki) = Softmax{ [qt · R(plocalt)] [krawi · R(plocali)]⊤ / √d }
式 (3)
R(·) 是旋转矩阵。关键在于 krawi 存的是没乘过 R 的键；每一步都用当下算出来的 plocali 现场乘。 缓冲区满时淘汰最老的非 sink 帧，sink 永久保留在 plocal = 0。三条保证：(a) 显存 O(Ks+Kr) 有界；(b) 所有位置都在分布内；(c) 淘汰不产生伪影。

06.1代码里的两条分支

这个设计在 modules/causal_model.py :: CausalSelfAttention.forward 里体现为一个 if/else，两条分支的差别正好就是模式 C 与模式 A：

modules/causal_model.py · KV-cache 推理路径（结构化节选）
  1. # ── 分支 C：local_rope_cap 打开 → 缓存原始 K，查询时现场旋转 ──
  2. kv_cache["k"][:, local_start:local_end] = k.detach() # 未旋转！
  3. offset = max(0, current_frame - local_rope_cap) # 即式 (2) 的 δ
  4. frame_abs = [0, history_start … current_frame-1, current_frame] # sink 恒为 0
  5. local_positions = clamp(frame_abs - offset, min=0) # 即式 (2)
  6. q_pos = [min(current_frame, local_rope_cap)] # 目标帧封顶在 C
  7. roped_q    = causal_rope_apply_with_positions(q, …, q_pos)
  8. k_for_attn = causal_rope_apply_with_positions(k_raw_for_attn, …, local_positions)
  9. x = flash_attention_4d(roped_q, k_for_attn, v_for_attn)
  10. # ── 分支 A：local_rope_cap = None → 绝对位置，缓存旋转后的 K ──
  11. roped_k = causal_rope_apply(k, …, start_frame=current_frame)
  12. kv_cache["k"][:, local_start:local_end] = roped_k.detach() # 已旋转，位置随 t 无限增长
注意第 4 行 frame_abs 的构造：数组第 0 位恒为 0（sink），中间是 arange(history_start, current_frame)，末位是 current_frame。 配合第 5 行的 clamp(..., min=0)，sink 帧的局部位置在任何时刻都是 0 —— 论文里「sink 永久锚定」这句话，实现上就是这两行的副作用。

06.2淘汰是一次 memmove，不是重建

缓冲区开 kv_window_size + 2 帧（sink ＋ 窗口 ＋ 当前）。写满之后，代码把 [2·fsl, end) 段整体前移一个帧长到 [fsl, end−fsl)， 下标 0 那一帧（sink）原地不动，然后把写指针回拨到 (W+1)·fsl。整个过程没有任何重新编码：

inference.py · 滑动窗口淘汰
  1. if local_end >= kv_buf_frames * fsl:
  2.   for cache in kv_cache:
  3.     cache["k"][:, fsl:evict_end-fsl] = cache["k"][:, 2*fsl:evict_end].clone()
  4.     cache["v"][:, fsl:evict_end-fsl] = cache["v"][:, 2*fsl:evict_end].clone()
  5.     cache["local_end_index"].fill_((kv_window_size + 1) * fsl)
因为存的是原始 K，前移之后不需要做任何相位修正 —— 下一步查询会用新的 local_positions 重新旋转全部键。这就是「淘汰无伪影」在实现层面的含义。
显存账

代码里直接给了公式：2 · L · F · fsl · H · d · 2 bytes。取 480×832（fsl = 390）、L = 30 层、H = 24 头、d = 128、bf16： kv_window = 12 → 缓冲 14 帧 → 约 2.0 GB；而不开滑窗跑 5 分钟（1200 latent 帧）则要 170 GB 量级，单卡直接 OOM。 滑窗不是「优化」，是长时程流式推理的入场券。

07Inference loop

推理主循环逐行走读：一帧到底发生了什么

开源仓库的 inference.py :: generate() 是整套设计的最终落点，全部逻辑不到 90 行。 下面按真实执行顺序拆成 7 步 —— 其中第 ④ 步是最容易被漏掉、但对正确性最关键的一步。

第 ④ 步为什么必须存在

去噪循环结束时，cache 当前槽位里存的是最后一次去噪迭代的含噪 K/V，而且那次迭代的 t > 0，意味着 cross-attention 是开着的。 如果就这样让它成为历史，后续帧读到的将是「带噪声、且带着上一帧动作标签」的上下文 —— §03 说的两个失效模式会同时出现。 第 ④ 步用 t = 0 重跑一次同一个位置，既把含噪 K/V 换成干净的，又因为 cross_attn_mask = (t > 0) 归零而把文本彻底挡在 cache 之外。 一次额外的前向换来两个不变量，我认为是这份实现里最漂亮的一处。

07.1采样器：不是 Euler，是「预测 x₀ 再重加噪」

蒸馏模型的采样器和标准 flow matching 的 Euler 更新不一样。代码里每一步做的是：

x̂0 = xσ − σ · fθ(xσ)　　→　　xσ′ = (1 − σ′) x̂0 + σ′ ε′,　ε′ ∼ 𝒩(0, I)
generate() 内联
即每一步都直接预测干净样本，再重新加噪到下一个噪声档位（restart 式采样），而不是沿 ODE 积分。 档位由 linspace(1, 0, n+1)[:-1] × 1000 给出：n = 2 → [1000, 500]，n = 4 → [1000, 750, 500, 250]。 调度器是 FlowMatchScheduler(shift=5.0, sigma_min=0.0, extra_one_step=True)，timesteps = shifted_sigmas × 1000，所以时间步数值除以 1000 就是当步的 σ。

09Three axes

实验：三条轴，每条排除一个混淆变量

论文的核心实验只做一件事：把「自然语言」和「动作索引」两种接口放在其他一切都相同的条件下比较。 对照组 Action-Index 把每个实体的动作表示成联合词表上的 one-hot，经一个可学习线性层投影进同一批条件层。

这个基线是被刻意加强过的

联合词表横跨两个 Boss，所以任何跨实体动作索引在技术上都能注入任一实体的上下文 —— 这一步排除了「输入层根本接不进去」这种平凡解释。 作者把它定位成键鼠输入、动画 ID、one-hot 动作 token 这一整类离散接口的 steel-man 抽象：它比原始低层控制强（拿到的是语义动作标签），也比典型的实体私有 ID 空间强（用的是共享联合词表）。 因此它在跨实体上的失败，反映的是索引接口缺少组合语义，而不是拿不到目标动作。

09.1评测协议：两套，绝对值不可互比

Prompt-injection 协议（轴 1–3）

① 从留出集随机取起始帧 → ② 先无条件热身约 2 s（32 帧，双方 prompt 都设为中性 idle）→ ③ t = 2 s 换成目标动作 prompt 并保持 3 s → ④ 标注员只看注入后的窗口打分。

测的是「组合式操控能力」

Trajectory-conditioned 协议（系统指标）

每模型 100 段留出的 10 s 片段，从第一帧开始，每一帧都喂真值动作字幕，无热身、无切换，最后二元判定整段是否跟上了动作序列。

测的是「轨迹保真度」

热身段的设计值得单独说一句：它切断了测试集续帧里可能泄漏的视觉线索。没有它，模型可以靠外推测试集轨迹「猜」出接下来要发生的动作，而不是真的响应 prompt。 代价是这个协议把视觉连贯性和语义服从性放在了最大张力上 —— 这也解释了为什么同一个学生在两套协议下的数字差得很远（跨实体 89% vs 系统级 90.4–93.2%）。

打分方式：每个条件 20 次试验（5 个起始帧 × 4 个随机种子），三名标注员在剥离接口身份与提示来源的盲测条件下按 {0 缺失, 1 部分, 2 完整} 打分，取中位数，ACA(≥1) 记为中位数 ≥ 1 的比例。 一致性：三对标注员的「差距不超过 1 档」比例在跨实体子集上为 96.5 / 96.0 / 95.0%，同分布子集上为 93.3 / 95.8 / 94.2%。

09.2轴 2 拆解：三个「难度层级」共同排除了单一混淆解释

跨实体这一轴，作者按源动作与目标实体原生动作库的视觉重叠度把 5 对动作分成三层，重叠度递增，也就是让 Action-Index 的「最近邻回退」机会递增。 如果语言的优势在三层里都成立，那它就不能被任何单一失效模式解释掉。

10.1实时是被流水线重排救回来的，不是被模型救回来的

11Ablations

消融：哪一个设计真的在撑着长时程

Stage 1 的 2×2 已经在 §03 里交互过了（结论：历史注意力类型是分水岭，文本范围几乎免费）。 这里看 Stage 2 的两个旋钮 —— 滑动窗口与 RoPE cap —— 在同一个蒸馏学生上的扫描结果。

对「cap 影响很小」这条结论的解读

作者自己给的机理解释很诚实，值得复述：在 Kr = 7 的滑窗下，目标帧与任一 recent 帧的相对距离本来就被构造性地夹在 [1, 7]， 完全落在训练见过的范围里。cap 真正约束的是目标帧到 sink 帧那段会无限增长的距离；而 sink 主要编码静态场景锚点，注意力质量本来就小， 所以它那里的 OOD 位置对 FVD 的影响有限。

换句话说：论文的第二个「界」在 FVD 这个指标上几乎测不出来。它的价值更可能体现在 FVD 测不到的地方（相位闪烁、极长时程的缓慢漂移）， 但论文没有给出针对性的指标。如果你要复现，我建议把 cap 当作一份廉价保险而不是性能来源。

12Appendix A.16

被放进附录、但很值得单读的一节：持久状态外挂环

逐帧可控 ≠ 长时程可玩。任何足够长的交互式视频里都存在实体级的离散状态：血量、阶段、任务进度。 这类状态在分钟尺度上演化，而生成器的注意力上下文只有 Ks+Kr+Kn = 9 个 latent token ≈ 1.75 s —— 中间差着约 100 倍。

作者给了一个我觉得很有说服力的实证：在 45 小时（30 h Margit ＋ 15 h Crucible Knight）含有大量玩家死亡与 Boss 死亡序列的数据上训练出来的模型， 从不会自发触发终局状态。它能忠实渲染每一次受伤动画，但永远不会把它们累加成一次状态跃迁。 这不是数据问题 —— 把上下文翻倍仍然差 50 倍，而且离散状态转移本来就不是视频预训练在优化的东西。

13Critical reading

局限与批判性阅读

先把作者自己承认的写清楚，再说我读下来的保留意见。这一节的目的不是唱反调，而是让你在引用这份工作时知道边界在哪。

13.1作者自陈的局限

  1. 标注通道：训练标签靠引擎内存插桩获得。作者强调这是测试床选择而非接口属性 —— 语言接口只消费「逐实体动作字幕」，不关心字幕从哪来（VLM 自动标注器、遥操作日志、机器人本体感知都能接），因此是数据侧问题。
  2. 开放词表的上界是文本编码器：编码器分布内概念的组合能自然外推，真正的新词仍需显式适配编码器。
  3. 连续控制不在射程内：接口面向语义动作，相机 SE(3) 轨迹、力/速度指令这类数值精确的控制需要另加一路连续通道与同一批条件层融合。
  4. episode 级状态靠手工模块：§12 的三段环是逐领域手写的，世界无关的可学版本仍是 open problem。
  5. 严格单智能体场景下，语言接口退化为离散输入的重命名，没有任何表征优势。这句是作者自己写在 §A.2 里的 —— 我认为它是全文最诚实的一句话，也直接圈定了这份工作的适用范围。

13.3我的保留意见

  1. 核心对照实验的样本量偏小。轴 2 是 5 对动作 × 20 次 = 每种接口 100 段；轴 3 是 4 个探针 × 10 次 = 40 段，而且只有 2 名标注员（其余处是 3 名），还事后剔除了 2 个候选探针。 配对 McNemar（49 : 3，Z = 6.38）在轴 2 上是有说服力的，但整体结论建立在几百段人工评分之上。
  2. A.10 是论证，不是实验。作者论证「更强的 Action-Index 基线（实体×动作分解表 ＋ 冻结文本编码器初始化）会塌缩回 NL」。 但冻结变体恰恰是最有意思的中间点：它同时拥有预训练语义先验和封闭词表。作者自己预期它「能收回大部分 Tier II / III 的差距」，却没有真的跑。 如果跑出来确实如此，那么诚实的结论应当收窄为「OOV 覆盖是结构性胜利，跨实体迁移的大部分收益来自预训练文本先验而非语言接口本身」—— 仍然是真结论，但比 89 vs 43 给人的印象要小。
  3. 容量不对称是承认了但没有被消解的。NL 侧接的是 UMT5-XXL（4096 维预训练编码器），Action-Index 侧是 one-hot → 可学线性层。作者的辩护是「拉平就等于把 NL 的表达力硬塞给对照组」，这在逻辑上成立，但也意味着这个对比测的是整条条件通路而非单纯的「接口」。
  4. FVD 变好可能以多样性为代价。2 步学生 FVD 反而优于 50 步教师（138.6 vs 206.2）。少步蒸馏落进分布高密度区是常见现象，论文没有报告任何多样性指标，也没有讨论。
  5. 「实时」的余量很薄，且依赖未开源组件。19.7 FPS 是单卡 H100 上的活跃计算吞吐（406 ms/chunk vs 500 ms 预算），且必须同时有 TAEHV 与双流重叠。二者都没随代码放出。
  6. 三实体泛化只有定性结果。Figure 1-ii 展示了「只训过双实体、直接跑三实体」，这是接口可扩展性最漂亮的证据，但没有对应的 ACA 数字。
  7. Stage 1 的 2×2 消融是在 256×448 上做的，而最终模型在 480×832。结论方向大概率成立，但「文本范围几乎免费」（201.9 vs 197.1）这种落在噪声量级的判断，在小分辨率上得出后直接外推到大分辨率，严格说证据是弱的。
  8. Table 3 的系统对比是自评。Genie 2/3 的「∼」、Solaris 的 FPS 判定都没有公开的判定协议。
但结论仍然成立的那部分

把上面所有折扣都打完，有一条论证是不依赖任何实验的：固定词表接口对词表外提示的覆盖率恒为 0，无论模型多大。 这是接口的定义决定的，不是性能问题。只要你相信「交互式世界模型迟早要支持用户临时说出一个没预定义过的动作」，这条就足以支撑「换接口」这个主张。 §09 的另外两条轴（同分布持平、跨实体领先）则是在证明「换了接口没有付出代价，而且顺带拿到了迁移能力」。这个论证结构本身是干净的。

14.2跑起来

环境与权重
  1. conda env create -f environment.yml && conda activate incantation
  2. # 只需要 Wan2.2-TI2V-5B 的 T5 / tokenizer / VAE，不需要 ~40 GB 的 DiT 教师权重
  3. huggingface-cli download Wan-AI/Wan2.2-TI2V-5B \
  4.   models_t5_umt5-xxl-enc-bf16.pth Wan2.2_VAE.pth --local-dir models/
  5. huggingface-cli download Wan-AI/Wan2.2-TI2V-5B --include "umt5-xxl/*" --local-dir models/
  6. huggingface-cli download MatrixTeam/Incantation_preview_margit --local-dir models/
  7. # 建议装 FlashAttention；否则会退回 PyTorch SDPA
推理（按论文配置，而非仓库默认值）
  1. python inference.py \
  2.   --model_path models/incantation-margit-preview.safetensors \
  3.   --image_path examples/start.png \
  4.   --actions_config examples/actions_example.json \
  5.   --height 480 --width 832 \ # 默认是 256×448
  6.   --num_inference_steps 2 \ # 默认是 4
  7.   --kv_window_size 7 \ # 默认 None＝全历史，务必显式打开
  8.   --local_rope_cap 16 # 打开它才会走「缓存原始 K」的分支
三个关键开关都不在默认值上。尤其 --kv_window_size：不传的话既拿不到长时程稳定性，显存也会随帧数线性涨（5 分钟 ≈ 170 GB 量级）。 另外 --local_rope_cap 不只是「封顶位置」—— 它同时切换了 KV 缓存存原始 K 还是存旋转后 K 这条代码分支（见 §06.1）。

14.3写动作脚本时的三个坑

  • 短的一方不会补 Standing，而是保持它的最后一个动作直到另一方结束（§02 的代码第 6–8 行）。想让某一方静止，显式写 ["Standing", 秒数]。
  • 时长会被量化到 0.25 s 的整数倍：_steps = max(1, round(duration / 0.25))，所以 0.1 s 和 0.25 s 是同一件事，1.6 s 会被吸附到 1.5 s。
  • 动作名必须逐字匹配 DURATION_MAP 的键，否则默认时长回退到 1.0 s（不会报错）。注意里面有一个大小写不一致的键 "Double Light blade upswing"。

14.4在 Awesome-Interactive-Video-World-Models 里怎么归类

按本仓库的分区定义，这篇最自然的落点是三个：

  • control · Action Control & Interfaces —— 这是它的主分区。整篇论文就是在回答「一个动作如何抵达生成器」，而且它给出的答案（逐实体语言槽）在本分区里是一个新的坐标点，而不是既有 action space 的变体。
  • systems · Interactive Video World Models —— 满足三条主线标准（可交互、视频生成、世界模型），有实时流式与 >5 min 时程。
  • realtime · Real-Time & Streaming Generation —— ODE 初始化 ＋ Self-Forcing 2 步蒸馏 ＋ RoPE 解耦 KV 滑窗，这一套是可以脱离「多实体」单独引用的。

次要相关：memory（§12 的 Observer–Tracker–Policy 是一个显式的外部状态持久化方案，与该分区里 LiveWorld / MultiGen 一类工作同源）、 datasets（128 小时、逐帧逐实体、零时间偏移的动作标注语料，若数据集全量放出会是该分区里少见的对抗性多实体资源）。
