Conv3D → 批量 Conv2D 精读

视频世界模型最后一步要用 VAE 解码器把潜变量还原成像素。在 Jetson Orin 上这一步很慢：作者对 Cosmos3-Nano 做了 profile（Edge 用的是字节级相同的 VAE），VAE 解码 GPU 时间的 96% 花在 3D 卷积上。论文不碰模型本身，只在运行时改写执行方式。主要的因果 Conv3D 时间核长度是 3，就把它拆成 3 次 2D 卷积，每个“时间抽头”一次。时间维折进 batch，三次结果相加，偏置只加一次，缓存语义保持不变。结果：解码快约 7 倍；Cosmos3-Edge 生成 25 帧的完整图生视频从 180.7 s 降到 81.9 s（2.21×）。按任何标准看，这都是一篇系统测量报告，不是模型论文。

我的判断。方法是对的，实现也细致。但“7 倍”该怎么读，要打个折：
  1. 数学上完全等价，账也对得上。我用 PyTorch 复现了 Algorithm 1，在 FP64 下与原算子差 ≤2.4×10−15。我还按 Diffusers 源码重建了调用序列。论文报告的调用数（67/101/169/237/305/441）、签名数（33/28）、编码器“169 次快速路径 + 12 次回退”，全部严丝合缝。
  2. 这个 7× 反映的是基线内核有多慢，而不是 Conv2D 本质上更快。稳态下两条路线的 FLOPs 完全相同。降阶只在前两个潜帧（缓存还不满时）跳过零填充，17 帧时一共只省 7.4%。按我算的 FLOPs，eager 基线实测只有 ≈2.06 TFLOPS。这只是 Orin BF16 张量峰值的约 5%，还低于 FP32 CUDA 核的峰值。同一台机器上，TensorRT 直接为这些 3D 卷积模块建引擎，就能快 9.1×。channels_last_3d、cudnn.benchmark、torch.compile、换 cuDNN 版本，这些便宜的调法论文一个都没试。
  3. 和 TensorRT 的比较，措辞偏向本文。“拿回 95.55% 的延迟降幅”这个说法没错，但换成加速比只有 73.5%，本文仍比 TRT 慢 36%。TRT 那边“99 个引擎、34 GiB 进程峰值内存”是最朴素的部署方式，有标准办法压下来。
  4. 跨模型证据偏弱。Nano 和 LingBot 都是单次测量，数据本身不满足“时间 ∝ 潜帧数”的直线规律。所谓“迁移到不同架构”，其实是同一个 Diffusers 类，在另一组通道宽度下复现了同一个慢内核。

§1一页读懂

它是什么

一个运行时补丁。它只改 Diffusers 里 WanCausalConv3d.forward 的执行方式，权重、时间缓存的读写顺序、卷积参数、偏置和输出布局都不变。遇到不支持的调用（比如时间步长 2 的下采样），就交回原生 Conv3D，并计数。补丁可以装上，也可以卸下。

它不是什么

不训练、不量化、不剪枝、不蒸馏，也不换解码器。它不评估世界模型的预测质量、交互质量或规划效果（§2、§7.3 自己说明了）。“世界模型”只是动机：规划时要想象多条未来，rollout 越快，能比较的方案越多。

为什么值得看

在 Orin 上，VAE 编码加解码占了 25 帧 I2V 的 64% 时间，而 50 步去噪只占 36%。如果换成少步蒸馏的世界模型，去噪变短，VAE 的占比只会更高（§5 可以拖动步数看）。流式逐块解码时，每次卷积在时间维上都很短，恰好是 3D 卷积内核最弱的区间。

§2背景：Wan VAE 为什么是“一个潜帧一个潜帧”地解码

要看懂这个优化为什么有效，先得知道这些 Conv3D 调用长什么样。论文 Table 1 概括成“时间短、空间大”。下面按 Diffusers 的 autoencoder_kl_wan.py 源码把它还原出来。

逐潜帧解码。AutoencoderKLWan._decode 对潜变量做一个 for 循环，每次只喂一个潜帧。第 1 个潜帧解出 1 帧像素，之后每个潜帧解出 4 帧（时间压缩 4×）。所以 17 帧视频对应 5 个潜帧，也就是 5 次解码器调用。

时间缓存。解码器里每个时间核为 3 的因果卷积，都要看前 2 帧。Diffusers 把每一层最后 2 帧存进 feat_cache（CACHE_T = 2），下一块开头拼回去。第 1 块没有缓存，前面补 2 帧零；第 2 块的缓存通常只有 1 帧；从第 3 块起才是完整的 2 帧。

每块 34 次调用。Wan2.2 解码器每块有 34 个 WanCausalConv3d：输入卷积 1、中间块 4、四级上采样块的残差卷积 24、时间上采样卷积 2（核 3×1×1）、通道变化处的 shortcut 2（1×1×1）、输出卷积 1。第 1 块会跳过 2 个时间上采样卷积；整段解码开头还有一次 post_quant_conv（1×1×1）。所以 n 个潜帧的总调用数是 1 + 32 + 34·(n−1)。

§3方法：把一个 3D 卷积拆成三个 2D 卷积

核心就是卷积定义本身。时间方向的核有 Kt = 3 个抽头，每个抽头 k 对应一个 2D 权重切片 Wk，作用在“往前数若干帧”的那一帧上。三个抽头各做一次 2D 卷积，结果相加就是原来的 3D 卷积。

Z = [C ; X]
缓存帧 C 拼在当前块 X 前面；拼完后的“有效左填充” pl = pbase − |C|。对 3×3×3 卷积 pbase = 2：无缓存补 2 帧零，缓存 1 帧补 1 帧零，缓存 2 帧不补。
qk(t)
输出第 t 帧时，抽头 k 读的是 Z 的第几帧。落到 Z 范围外（也就是零填充区）的贡献为 0，可以整块不算。
[ol, oh)
抽头 k 的有效输出区间，δk = k·dt − pl，ol = max(0, −δk)，oh = min(To, |Z| − δk)；对应源区间 [ol+δk, oh+δk)。两段一样长，而且都是连续的，所以能把这段时间直接折进 batch，用一次 Conv2D 算完（式 (4)）。
b
偏置只加一次。每个抽头都加一次的话会变成 3b，这是最容易犯的错。

我的复现

我按式 (1)–(4) 用约 40 行 PyTorch 写了 Algorithm 1（拼缓存 → 逐抽头求区间 → 折 batch → Conv2D → 累加 → 加一次偏置 → 还原布局），直接与 Diffusers 的 WanCausalConv3d 比较：

  • 27 种运行时状态：时间核 {3×3×3, 3×1×1, 1×1×1} × Tin ∈ {1, 2, 4} × 缓存 ∈ {无, 1 帧, 2 帧}。FP64 下最大误差 2.4×10−15。
  • 时间膨胀 dt = 2（Wan 用不到，论文 §4.2 声称也成立）：缓存 {无, 2, 4} 帧，误差 ≤1.1×10−15。式 (4) 把膨胀并进 δk，确实正确。
  • 每个输出帧的每个有效抽头都只算一次，偏置只加一次，这是论文说的 “add b once”。

这里验证的只是数学。论文在 Algorithm 1 里写了护栏条件，但没有代码，权重缓存、布局细节和计时脚本都无法核对（§9-12）。

§4为什么会快 7 倍？——算得不比原来少，是基线内核太慢

论文把加速归因于“短时间、大空间的调用适合批量 Conv2D”，但没有拆开解释快在哪里。我按 §2 的源码调用序列逐次计算了 FLOPs，再用论文的实测时间去除，结果很清楚。

两条虚线是参照：Orin 64 GB 的 FP32 CUDA 核峰值 5.3 TFLOPS（NVIDIA 技术简报），以及 BF16 稠密张量核峰值 ≈42.5 TFLOPS（由 GPU 的 170 稀疏 INT8 TOPS 折算：去掉稀疏 ÷2，INT8 换 BF16 再 ÷2）。
几个数值都偏保守：分母里还算了归一化、激活、注意力、拼接这些非卷积开销。即便如此，eager 基线的 BF16 Conv3D 只跑到 ≈2 TFLOPS，还不如不用张量核的 FP32 峰值。Nano 的 Nsight profile 可以独立印证：252.7 TFLOP 的 Conv3D 用了 139.91 s，≈1.8 TFLOPS。TensorRT 直接为这些 Conv3D 模块建引擎，达到 ≈18.7 TFLOPS（内部选了什么内核，论文没说）。可见 3D 卷积本身在这块芯片上并不慢，慢的是 PyTorch 2.11 + cuDNN 9.19 在 NCDHW BF16 下选中的那个内核。论文说这个“implicit BF16 3D 卷积内核族”占了 75.6% 的内核时间，但没有报告它的吞吐，也没有追问原因。

同类“慢 Conv3D”在公开记录里并不少见

  • PyTorch 2.9.0：AMP 下 3D 卷积约 4× 回归，改走 vol2col；换 cuDNN 9.16 可修复（#166122）。
  • cuDNN 9.1 在 H100 上的 BF16/FP16 Conv3D 回归报告（NVIDIA 论坛）。
  • ROCm/MIOpen：原生 Conv3D 只有在只输出 1 帧时快，多帧块落到 Im3d2Col；改成逐抽头 Conv2D 后，17 帧编码从 103 s 降到 2.4 s（InvokeAI-7 #289）。
  • 反方向的例子：HartsyInference 在 4090 上把逐抽头 2D 改回原生 3D + channels-last，Wan2.2 解码的卷积时间从约 69 s 降到约 16 s。PR 里还说，同一个 BF16 3×3 卷积在 NCHW 下约 40 TFLOPS，channels-last 下 155–165（#174）。

所以“拆成 2D 快还是原生 3D 快”取决于内核实现和内存布局，没有普遍答案。

论文该先排除、但没做的对照

  • x.to(memory_format=torch.channels_last_3d)：让 cuDNN 走 NDHWC 张量核路径。
  • torch.backends.cudnn.benchmark = True：让 cuDNN 实测挑算法，而不是用启发式。
  • torch.compile / AOTInductor。Cosmos 3 技术报告 §5.2.6 对同一个 Wan2.2 tokenizer 就是这么做的：按“首块 / 缓存 1 / 缓存 2”三种状态分别编译，编码延迟再降 52%（那是训练时在数据中心 GPU 上、叠加在分块编码之上的结果，不能直接搬到 Orin）。
  • 换 cuDNN 版本，或者 FP16、FP32 基线，用来判断是不是某个版本的回归。
  • 更大的时间块（同一节：每次调用多喂几帧，提高算术强度）。

这些都不改权重，也都是“运行时优化”。任何一个都可能明显压缩 7× 这个数字。

怎么读这个 7×

准确的说法是：在“Jetson AGX Orin + PyTorch 2.11 + cuDNN 9.19 + NCDHW BF16 + 默认设置”这套软件栈上，把 Conv3D 改写成 Conv2D，可以绕开一个比应有速度慢约 7 倍的内核。这个绕法本身有价值：可移植，不需要编译，也不需要为每个形状建引擎，所以是很好的兜底方案。但它不是“Conv3D→Conv2D 的一般规律”。我手上没有 Orin，无法替论文补这些对照。

一段本不需要的编码

我查了 Diffusers main 分支里 Cosmos3OmniPipeline.prepare_latents 的源码。I2V 模式会把条件图复制成 num_frames 帧，整段送进 VAE 编码。但它只把第 0 个潜帧当条件（vision_condition_mask[0] = 1），其余潜帧马上被纯噪声替换。Wan 编码器是因果的，第 0 个潜帧只依赖第 1 帧像素。所以只编码第 1 帧，得到的条件一模一样。Table 3 的编码时间随帧数线性增长（5 帧 5.3 s，25 帧 25.6 s），和这一点吻合。

勾上开关，就能看到这对结论的影响（粗估：编码成本按帧数线性折算）。25 帧基线从 180.7 s 降到约 156 s，这一步不需要任何算子改动。本文的端到端加速也相应从 2.21× 降到约 2.0×。论文用的是 Diffusers 0.40.0.dev0 @ b48d49d8，与我读的 main 可能有出入，但计时规律支持这个判断。另外，摘要说完整生成“快 2 倍以上”，只对 25 帧成立，5 帧是 1.85×。

§6三套解码器的数据重读：用“时间 ∝ 潜帧数”做体检

Nano 与 LingBot：单次测量，而且自相矛盾

Nano 基线每多一个潜帧的增量依次是 12.9 / 36.5 / 36.7 / 27.6 s，5 帧点偏离直线 +66%。它 17 帧的基线 106.45 s，也对不上自己的 Nsight profile（VAE GPU 时间 145.82 s）。按 Edge 的实测效率外推，应在 142 s 左右。LingBot 的降阶路线从 5 帧到 9 帧只多了 0.02 s（5.27 → 5.29），这不可能。所以“2.70×”大概率是测量问题。

结论：三套解码器都有约 5–7× 的量级加速，这一点可信。但论文给的“4.74–6.65×”“2.70–5.75×”区间，以及它们随帧数的变化，不要细读。“跨架构迁移”也要打折：Wan2.1 和 Wan2.2 在 Diffusers 里是同一个 AutoencoderKLWan 类、同一个 WanCausalConv3d、同一套缓存逻辑，区别只在通道数、is_residual 和 z 维。能跑通几乎是必然的，加速只说明同一个慢内核在 96/192/384 通道上也一样慢（§9-04）。

§7和 TensorRT 比：数字都对，措辞偏向本文

这组对照在干净环境里做：MAXN 模式、jetson_clocks、GPU/EMC 频率固定在 1300.5/3199 MHz，每条路线 6 次、平衡顺序、每次一个新进程。TRT 用了 99 个“把学到的权重烤进去”的定形引擎，覆盖 33 种运行时签名，也就是全部 169 次调用。

TRT 这边，是最“重”的一种配法

99 个 execution context 各带一份激活显存，一共 13.87 GB。而 TensorRT 允许由用户管理、在多个 context 之间共享同一块 device memory：顺序执行时，只需要最大的那一份。引擎也可以只按 33 种签名建，权重可以 refit，甚至可以给整个解码块只建“首块 / 缓存 1 / 缓存 2”三种形状的引擎。论文都没试，所以 14.57 GiB 峰值分配、34.19 GiB VmHWM 和 1637.6 s 构建时间，应当看作朴素部署的上限。论文 §7.2 也承认，选择性加载或逐出“我们没有评估”。

本文这边，也有 1 GB 可以省

本文路线的峰值 CUDA 分配从 5.37 升到 7.31 GiB（+1.94 GiB），VmHWM 从 8.23 升到 9.75 GiB。其中缓存的抽头权重切片占 1.06 GB。我按源码数了一下：Wan2.2 解码器全部 WanCausalConv3d 的权重是 529.6M 参数，BF16 下正好 1.059 GB。也就是说，整套 Conv3D 权重被复制了一份。原因是 W[:, :, k] 在原布局下不连续，每个切片都要 contiguous() 一次。如果一次性把权重重排成 (Kt, Cout, Cin, Kh, Kw) 再释放原张量，这 1 GB 就能省掉。

§9存疑清单

按对结论的影响排序。“高”会改变你对标题结论的理解，“中”削弱某个分论点，“低”是细节、笔误或复现问题。每条都附了可以自己核对的证据位置。

01高基线很可能是一个“没调好”的 Conv3D，而论文没有排除最便宜的几种调法

我按 Diffusers 源码逐次统计了 17 帧 Edge 解码的 FLOPs：Conv3D 109.5 TFLOP，上采样里的 Conv2D 17.1 TFLOP。除以实测时间，eager 基线只有 ≈2.06 TFLOPS，约为 Orin BF16 张量峰值的 4.8%，还低于 FP32 CUDA 核峰值 5.3 TFLOPS。Nano 的 profile 反推也是 ≈1.8 TFLOPS。降阶后是 ≈13.75，TRT 是 ≈18.7，而 TRT 是直接为这些 Conv3D 模块建的引擎。也就是说，Conv3D 在这块芯片上本来可以很快。

论文没有试 channels_last_3d、cudnn.benchmark、torch.compile/AOTInductor（Cosmos 3 技术报告对同一个 tokenizer 用了），也没有换 cuDNN 版本或精度。公开记录里，半精度 Conv3D 走慢路径的事并不少见（§4）。还有反例：HartsyInference 在 4090 上从逐抽头 2D 改回原生 3D，反而快了约 4 倍。所以“7×”应读作“绕开了这套软件栈上一个慢内核”，而不是“Conv3D 拆成 Conv2D 本质上快 7 倍”。

证据：Table 4、Table 6、§3.1 的 75.6% 内核占比；我的 FLOPs 计算见 §2、§4。

02高与 TensorRT 的比较：算术没错，但度量选得有利，TRT 配置也是最重的一种

“拿回 95.55% 的延迟降幅”算术正确，但基线慢了 9 倍，这个比例天然偏高。换成加速比是 73.5%，按对数算是 86%，而本文仍比 TRT 慢 1.36×。

TRT 的 99 个引擎各自带 execution context，激活显存一共 13.87 GB。TRT 支持多个 context 共享用户提供的 device memory，也可以按 33 种签名建可 refit 的引擎，或者按整块只建 3 种形状。这些论文都没试，所以 34.19 GiB VmHWM 是朴素部署的上限。1637.6 s 的 AOT 构建约 673 次解码就能回本，对“固定模型、长期运行”的机器人不算重。

论文真正站得住的优势是零构建、易维护、覆盖任意形状，而不是“几乎一样快”。

证据：Table 6，§5.4、§6.4、§7.2。

03中Nano 和 LingBot 的数据自相矛盾，加速区间不宜细读

从第 3 个潜帧起，每块形状相同，解码时间应当随潜帧数线性增长。Edge 完美符合，R² = 1.00000。Nano 不符合：基线每多一个潜帧的增量是 12.9 / 36.5 / 36.7 / 27.6 s，5 帧点偏离 +66%。它 17 帧的基线 106.45 s，也对不上自己的 profile（145.82 s）。LingBot 的降阶路线从 5 帧到 9 帧只多了 0.02 s，5 帧点偏离 +33%。这两组都是 n = 1。

“约 5–6×”的量级可以相信，“4.74–6.65×”“2.70–5.75×”的区间和变化趋势不要解读。

证据：Table 4；§3.1 与 Table 4 的 Nano 17 帧数字；图 7。

04中“迁移到不同架构”其实是同一个类、同一个内核问题，换了通道宽度

在 Diffusers 里，LingBot 的 Wan2.1 VAE 和 Wan2.2 VAE 是同一个 AutoencoderKLWan、同一个 WanCausalConv3d、同一套 feat_cache 协议。降阶只改这个类的 forward，所以能跑通几乎是必然的。

真正有说服力的迁移证据，应该来自缓存协议和写法都不同的因果 VAE，比如 HunyuanVideo、LTX-Video、CogVideoX 的 VAE 或 Cosmos tokenizer；或者来自别的硬件，比如 Orin NX/Nano、Thor、桌面 GPU。论文 §7.1 自己把结论限定在“Wan 家族 + Diffusers 实现”，但摘要里的 “architecturally distinct” 说得更宽。LingBot 也只用合成潜变量测了解码器。

证据：摘要、§6.2、§7.1、§7.3；Diffusers autoencoder_kl_wan.py。

05中端到端 2.21× 里，有一部分来自加速一段“本不必要”的编码；“2 倍以上”只对 25 帧成立

Cosmos3OmniPipeline 的 I2V 会把条件图复制成 F 帧整段编码，却只用第 0 个潜帧当条件。因果编码器的第 0 个潜帧只依赖第 1 帧，所以只编码第 1 帧，结果完全相同。粗估：修掉之后，25 帧基线就降到约 156 s，本文的端到端加速也降到约 2.0×。摘要说完整生成“快 2 倍以上”，但 5 帧只有 1.85×。

证据：Table 3 编码时间随帧数线性增长；Diffusers main 的 prepare_latents（论文用的 commit b48d49d8 可能略有不同）。

06中新颖性有限，也没讨论已有的同类实现

式 (2) 就是卷积定义按时间抽头展开。论文引用的 P3D、R(2+1)D 是学出来的因式分解，不是同一回事。在推理框架里，这个改写在论文挂上 arXiv（2026-09-25）之前已有公开实现：InvokeAI 的 ROCm 分支把 Wan VAE 的因果 Conv3D 逐抽头拆成 Conv2D，2026-09-19 的修复 PR 里写明了“原生 Conv3D 只有单输出帧时快”。同一时期，stable-diffusion.cpp、ComfyUI（ROCm）和 vLLM-Omni 也有单帧版本的 PR；论文还引用了 vLLM-Omni，却没提这些。

论文真正的增量是三样：带护栏的缓存感知实现、Jetson 上的系统测量、TRT 对照。

证据：§2 相关工作；§4 的链接。

07低数值一致性只比了两个近似之间，没有高精度参照，累加精度也没写

Table 5 比的是 BF16 对 BF16。我的单层实验显示：若累加用 BF16，降阶相对 FP64 的 RMSE 比原生大约 41%；改成 FP32 累加只大约 15%。量级都很小。建议补充：用真实潜变量，报告相对 FP32 参照的误差和 PSNR。Edge 与 LingBot 用的是合成潜变量。

证据：Table 5，§6.3；我的实验见 §8。

08低1.06 GB 的抽头切片，正好是整套解码器 Conv3D 权重的副本

529.6M 参数 × 2 字节 = 1.059 GB，与论文数字一致。权重一次性重排再释放原张量，就能省掉这份副本。按抽头折 batch 时，如果每次都重新 permute，也会产生多份输入拷贝。对 64 GB 的 AGX Orin 无所谓，但论文恰恰以“给其他模块留显存”作为相对 TRT 的卖点。放到 8/16 GB 的 Orin Nano/NX 上，这一点就要紧了。

证据：§6.4；我按源码统计的参数量。

09低只有一台设备，只测新进程里的第一次正式解码

所有结论都来自一台 64 GB AGX Orin，也就是 Orin 家族里最大的一款。每个点都是“新进程 + 1 次预热 + 1 次计时”，不代表规划循环里反复调用的稳态，也没有与感知、控制并发。没有整板功耗。论文 §7.3 自己承认了这些。

10低“干净环境”下降阶路线反而慢了 7%，没有解释

Table 4 的 17 帧 Edge：eager 61.573 s，降阶 8.623 s（7.14×）。Table 6 固定了时钟：eager 61.72 s（+0.2%），降阶 9.23 s（+7.0%），加速变成 6.69×。eager 几乎不变而降阶变慢，说明降阶路线对某个环境因素更敏感，可能是频率、内存状态或进程状态。

11低几处表述与源码或论文自身数字对不上
  • §3.2 说 LingBot 的所有调用“时间核大小都是 3”。但按源码，同一段报的 164 次调用里有 6 次是 1×1×1：5 次残差 shortcut，1 次 post_quant_conv。
  • Table 1 Nano 第 3 行（1024→1024，2→2，90×160，Tc=2）写 15 次调用。按源码应为 18 次：上采样第 1 级有 6 个卷积，乘以第 3–5 个潜帧。同表另两行的 15 次是对的。
  • Table 3 降阶 25 帧：4.024 + 65.142 + 13.027 = 82.193 s，而表中完整生成是 81.935 s。各阶段分别取中位数会造成这种差异，但 Tdit+other 本来就是用减法定义的。
  • §7.2 的 Triton 集成实验写“解码 16.01 → 66.81 s”。这个 16.01 s 和本文任何一个 17 帧数字都对不上（Edge 8.62/9.23，Nano 18.30），实验配置也没交代。

另外核对通过的：Table 3 的全部加速比；237 = 33 + 34×6；编码器 169 + 12；33/28 种签名；196 个参数张量；95.55%。

12低没有代码

论文没有给代码链接（2026-09-29 查）。方法本身短到可以自己复现（§3），但护栏条件、权重缓存、布局细节、计时与验收脚本都无法核对。

13低“世界模型”只是背景：没有规划或 rollout 实验，加速后离交互式仍然很远

25 帧（约 1 秒视频）的 I2V 加速后仍要 81.9 s，其中去噪占 65.1 s。引言强调规划要比较多条 rollout，但论文没有做任何规划实验，§2 也声明不评估预测质量。对交互式世界模型，应当读作“VAE 这一段可以便宜地快 5–7 倍”，而不是“Orin 上的世界模型已经能用了”。

§10公道话，以及对交互式视频世界模型的启示

做得扎实的地方

  • 路由计数 + 验收标准。基线必须 0 次快速路径命中，优化必须 0 次意外回退，输出要形状正确、无 NaN/Inf。这是做运行时补丁的好习惯。
  • 来源核对。用 SHA-256 确认 Edge 与 Nano 的 VAE 字节级一致，196 个参数张量都对得上。论文也明确说 Nano 的 profile 不能直接当作 Edge 的。
  • 主动报告不利结果。TRT 更快；Triton 集成后反而变慢；编码器有 12 次回退；有热状态切换，所以不声称没有降频；统一内存下不把 RSS 和 CUDA 显存相加。
  • 账目细致。除 Table 1 的一处调用数（§9-11），其余调用数、签名数和 1.06 GB 都与 Diffusers 源码吻合。我逐一核过。

对交互式世界模型的启示

  1. 流式或因果 VAE 逐块解码，每次调用的 T 都很小，这正是 3D 卷积内核最弱的区间。先量一下自己 VAE 的实际 TFLOPS。如果远低于峰值，就有便宜的空间可挖。
  2. 先试不改权重的便宜旋钮：channels_last_3d、cudnn.benchmark、torch.compile、换 cuDNN 版本。再把逐抽头 Conv2D 当作可移植的兜底方案。
  3. 少步蒸馏之后，VAE 会变成主瓶颈（图 6 把步数拉到 4 试试）。自回归世界模型每生成一块就要解码一块，这一段的效率直接决定交互帧率。
  4. 图生视频或动作条件的世界模型，不要把复制出来的条件帧整段送进编码器。
  5. 形状固定、长期运行的部署，TRT 或 AOT 的构建成本很快就能摊薄。注意共享 context 内存。
最值钱的补充实验
  1. 在同一台 Orin 上补四个 eager Conv3D 对照：channels_last_3d、cudnn.benchmark、torch.compile、另一个 cuDNN 版本，并报告每种的 TFLOPS。
  2. Orin NX/Nano、Thor 和一块桌面 GPU 上的同一组测量，看 7× 是否只是某个平台的现象。
  3. 至少一个非 Wan 的因果视频 VAE。
  4. Nano 与 LingBot 每点至少测 3 次。
  5. 用真实潜变量，报告各路线相对 FP32 参照的误差和 PSNR；写明累加精度。
  6. 共享 context 内存、按签名建引擎的 TRT 对照。
  7. 修掉冗余编码之后的端到端数字。
