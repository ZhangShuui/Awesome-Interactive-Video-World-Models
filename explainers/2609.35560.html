WorldPlay2 精读把控制拆开、把历史压扁、把蒸馏稳住——一个在 8×H20 上跑 16 FPS 的交互式世界模型

WorldPlay2: Extending Real-Time Interactive World Models in Control and Horizon。它是 WorldPlay（开源名 HY-World 1.5）的续作。本页先补齐读懂它所需的背景，再把三件事——因子化混合控制、面向蒸馏的压缩记忆、Stable Forcing——拆开讲清楚，最后复算所有能复算的数字，列出存疑点。

一句话把“动作”（逐潜帧的键鼠）和“语义”（场景 / 角色 / 事件三段式字幕）分开喂给模型；把全部历史压成约 1/32 长度的记忆 token，而且学生和老师共用同一种记忆，于是 320 个潜帧的长 rollout 可以切成 10 段、每段各自交给老师打分；蒸馏前先用 PDD 做少步初始化（让学生用少数几次前向走完老师的多步轨迹），蒸馏时每块都完整走完 4 步再写进记忆，只在随机一步上回放梯度。

01一句话与定位

交互式世界模型要同时满足三件事：能接多种控制（走、转、跳，也要能“下起雨”“拉开车门”）、长时程一致（转一圈回来，房子还在原地）、实时。作者认为前人卡在两处：一是控制信号彼此异构，难以统一建模；二是长记忆让蒸馏既贵又不稳。

贡献 ①

因子化混合控制

低层运动用逐潜帧对齐的动作向量：俯仰 / 偏航是连续值，前后、左右、视角、跳跃是离散值，在每个 Transformer 块的 FFN 之前注入。高层语义用三段式结构化字幕：scene（场景）、character（角色外观）、event（正在发生的事）。按附录的字幕模板（每段视频只写一个 scene、一个 character），场景和角色字段跨块不变，变的只有事件（这是从模板推断的，正文没明说）。

贡献 ②

面向蒸馏的压缩记忆

历史 = [sink ; 压缩 token ; 最近邻 token]。压缩器沿用 TinyHistory 的双分支结构（低清低帧率主干 + 高清残差），序列约缩短 32 倍。关键在于双向老师也用同一种记忆：老师只需看“一段 32 潜帧 + 记忆”就能打分，不必一次吞下整条 rollout。

贡献 ③

Stable Forcing

① PDD 少步初始化：先让 AR 学生学会用少数几次前向走完老师的多步轨迹（最终学生是 4 步）。② 全程回放：rollout 时每块都完整走 4 步，只拿终稿写进记忆；同时随机记下某一步的输入，事后带梯度重放。③ 分段打分：320 潜帧切成 10 段，每段带着记忆交给老师和评论家打分。

我的总体判断

这篇真正的亮点是贡献 ②：让记忆的形态服务于蒸馏。压缩记忆既让推理变便宜，也让“长 rollout + 带记忆的老师”这种 DMD 蒸馏能按段线性扩展。它是前作 Context Forcing（让老师与学生看同一份记忆）的自然推进。

贡献 ③ 里，数字显示贡献最大的是 PDD 初始化（表 8：+7.9 分）；全程回放在没有初始化的条件下只带来 +1.3 分，而且表里缺“有初始化、无回放”这一格，没法单独评估回放。

评测上，两张王牌——RevisitBench 和事件响应——都是自建的：前者的轨迹结构和自家 UE 回环训练数据如出一辙，后者的测试样本有一部分来自自家事件数据集；“因子化”本身的收益也缺少干净的对照实验。结论：方法可信、工程扎实，但领先幅度要打个折看。

02先补课：潜帧、块、段、rollout

视频先由 VAE 压成潜帧（latent）。按前作的约定（因果 VAE 的通行做法），1 个潜帧 ≈ 4 个视频帧，第一帧单独编码，所以 T 个潜帧对应 4(T−1)+1 帧。4 个潜帧组成 1 块（chunk）= 16 帧，这是自回归一次生成的单位。所谓“16 FPS 实时”，就是每块大约 1 秒内生成完。老师打分的一段（clip）= 32 潜帧 = 8 块；蒸馏时学生一口气自展开 320 潜帧 = 80 块 = 10 段。

流匹配（flow matching）

xσ = (1−σ)x + σε，网络预测速度 v = ε − x（式 5 的回归目标）。σ 从 1（纯噪声）走到 0（成片）。“少步”就是只用 4 次网络调用走完这条路。

自回归学生 / 双向老师

学生只能看过去（因果掩码），一块接一块地流式生成；老师在一段之内前后都能看，质量更高，但不能流式。蒸馏就是让学生的输出分布向老师靠拢。

DMD（分布匹配蒸馏）

把学生生成的样本加噪，分别交给“真实分数”（冻结的老师）和“伪分数”（在线训练的评论家，专门拟合学生当前的分布）。两者之差指明“往哪个方向改，更像真实数据”。

Self Forcing 与 exposure bias

训练时如果总拿干净的真视频当历史，推理时却只能用自己生成的、带误差的历史，误差就会一块块滚雪球（exposure bias）。Self Forcing 让学生在训练时也用自己生成的历史继续往下生成，从而对齐训练与推理。

04控制接口：动作与语义分开走

论文的出发点：相机转动、角色走路需要逐帧精确；“拉开车门上车”“天开始下雨”这类事件本来就跨好几秒，更适合用高层语义描述。硬把两类信号塞进同一种表示，模型容易把“画面长什么样”“往哪儿动”“发生了什么”搅在一起。

4.1 帧对齐动作

(1)et = E(continuous) + e[discrete]
(2)h̃t = ht + F( [ ht ⊕ et ] )

翻成人话：连续部分（俯仰角、偏航角）过一个小 MLP E；离散部分（前 / 后 / 不动、左 / 右 / 不动、第一 / 第三人称、跳）各查一张嵌入表；加起来就是这个潜帧的动作向量 et。然后在每个 Transformer 块里、FFN 之前，把 et 按通道拼到这一潜帧的每个 token 上，过辅助 MLP F，结果作为残差加回去。

为什么敢扔掉相机位姿

前作用 PRoPE 把完整的相机外参注入注意力，一个重要用途是给“按位置检索记忆”提供坐标。v2 改成压缩全部历史、不再检索，位姿就不是刚需了。作者还给了一个理由：强制刚性相机轨迹，很难模拟以角色为中心的转身（第三人称里“向左转”其实是绕角色公转，而不是相机原地自转）。论文称去掉位姿“没有可见的退化”，但没有给定量对比。间接证据是 WBench 导航项 88.3 对前作 86.8。

4.2 结构化语义控制

(3)dt = ( dscene, dcharacter, devent )

scene 描述环境：空间布局、物体、光照、画风；character 描述被控角色持久不变的身份与外观（第一人称时为 None）；event 描述当前事件带来的语义变化：操作物体、环境变化、物体出现 / 消失。关键在于：按字幕模板，前两个字段每段视频只写一次，因而跨块不变，只有 event 在变（这是从模板推断的，正文没明说）。模型因此能学到“event 里的字变了，不该连带着把人和场景重画一遍”。

05压缩记忆：历史压成 1/32，但不是全部都压

  
(4)m<t = [ xsink ; xcmp = Cφ( x<t, xlr<t ) ; xtmp ]

  
记忆由三部分拼成：sink——论文只说它“提供稳定参照”；按前作惯例（保留第一块做注意力 sink 能减轻漂移），推测是视频开头的一段、全分辨率；压缩 token——把全部历史压成约 1/32 长度；tmp——“相邻的时间 token”，保证块与块之间衔接平滑（推测为全分辨率）。TinyHistory 原文里，给纯压缩记忆加一个 3 潜帧的全分辨率滑窗，场景一致性从 72.2 升到 82.5（+10.3），是它所有扩展里提升最大的一项；v2 的 tmp 就是这一招。


  

  

    一个没交代的推理细节
    
粗分支的输入是“低清、低帧率的视频经 VAE 编码的潜码”。训练时这很自然（手里就有真视频）；可推理时和蒸馏 rollout 时，历史是模型自己生成的潜帧——要得到 xlr，似乎得先解码成像素、缩小、再重新编码。这一步的开销有没有算进每块 0.998 s，用的是原 VAE 还是 LightVAE（后者会让训练与推理的输入分布不同），论文都没说。

  


  
压缩比到底是多少：记忆预算计算器

  
论文说序列缩短约 l·s² = 2×4² = 32 倍。这只对中间压缩段成立；若 sink 和 tmp 保持全分辨率（论文没写，但“稳定参照”“相邻时间 token”的定位让这很可能），有效压缩比取决于它们的长度和已生成的长度。下面的默认值是我的假设（论文没给）：sink = tmp = 1 块 = 4 潜帧；每潜帧 token 数按 HunyuanVideo-1.5 的 16× VAE 在 480p 下的 30×53 = 1590 估算。

06共享记忆 → 分段打分：为什么蒸馏突然变便宜了

  
DMD 需要老师给学生生成的视频打分。如果老师必须看全部上下文，一条 320 潜帧的 rollout 就是一条几十万 token 的序列——论文报告全上下文老师在 320 潜帧时直接显存溢出。v2 的做法是：既然老师也用压缩记忆，就把 rollout 切成 10 段、每段 32 潜帧，每段带上“它之前所有块”的压缩记忆，分别打分。

  
(7)sfake/real = v( xσ[iL:(i+1)L], σ, m<iL, A≤(i+1)L )


  

  

    “长时程监督”只走记忆这一条路
    
老师在第 i 段回答的问题其实是：“给定这段历史（的压缩版），这一段像不像真视频？”历史用的是学生自己生成的内容，所以打分检查的是“与自己的过去一致”，而不是“与某个真实视频一致”——这正是 Self Forcing 想要的。代价是：被压缩丢掉的细节，老师也看不到，自然也无法要求学生保持它。长时程一致性的上限 = 压缩记忆保住的信息量。

    
谱系上，这是前作 Context Forcing（“老师与学生看同一份记忆，否则分布对不齐”）的推广；RELIC 走的是另一条路：训练一个 20 秒全上下文老师，再用梯度回放扛住显存。v2 把记忆压小，让“对齐记忆”可以沿时间线切段、线性扩展。

  







  
07Stable Forcing：先学会少步，再全程展开

  
长 rollout 加少步采样，误差会跨块迅速累积，学生的分布越来越偏离老师，DMD 训练随之发散。作者给了两剂药：开局就要稳（PDD 少步初始化），以及写进记忆的东西要干净（全程回放）。


  
7.1 PDD 少步初始化

  
(6)ℒPDD = 𝔼k∈[0,C−1] ‖ uk − sg( Nθ( xtσik, σik, m<t, A≤t ) ) ‖²

  
PDD（Parallel Decoding Distillation，NVIDIA，2607.26004）用人话讲：老师本来要走 N 小步。把这 N 步每 C 步分成一大块（v2 的记号：K 块 × C 个子区间）。给学生装上多个输出头：站在一大块的起点，一次前向同时预测接下来 C 小步各自的平均速度。训练时，沿学生自己预测的小步往前走，在随机一个中间点上问老师“这一小步你会怎么走”，用老师的答案监督对应的那个头（on-policy）。推理时，C 个头按步长加权融合成一个线性层，一步跨过整个大块。PDD 原文命题 1：若损失降到零，学生用 N/C 次前向精确复现老师的 N 步轨迹。


  
  

    和常见的 ODE 初始化比呢？
    
CausVid、Self Forcing、RELIC 的惯例是“ODE 初始化”：离线采老师的去噪轨迹，让学生在 4 个固定时刻上回归。PDD 的不同在于 on-policy（在学生自己走出的中间状态上问老师），并把一大步拆成 C 个小步分别监督。可 v2 没有与 ODE 初始化对比；表 8 的 “w/o init” 到底是“完全不初始化”还是“换成 ODE 初始化”也没说。所以“PDD 优于常规初始化”这一点，本文并未证明。

  


  
7.2 全程回放：写进记忆的必须是终稿

  
Self Forcing 为了让少步生成器的每一步都得到监督，会随机选一个停止步 s：只去噪到第 s 步，就把这一步的 x̂₀ 预测当作该块的输出写进后续块的上下文，梯度也只落在这一步。（抽样粒度：Self Forcing 原文算法按迭代抽一个 s、各块共用；前作 Context Forcing 的算法 1 是每块各抽一个。）这在 5 秒的短 rollout 里问题不大；可在 80 块的长 rollout 里，s 有 3/4 的概率小于 4——要么整条 rollout 都用“半成品”写记忆，要么约 3/4 的块是半成品，后面每一块都得踩着它们往下生成。v2 的改法：每块都完整走 4 步，只拿终稿进记忆；同时随机选一步 di，把这一步的输入（噪声潜码、σ、记忆、动作）拍个快照，等打完分后再带梯度重放这一步。

  

  
7.3 一个没被讨论的近似：终稿打分，改在中间稿上

  
算法 1 的第 3 阶段里，损失写作 MSE( x̃i, sg(x̃i − gi) )。其中打分向量 gi 是在走完 4 步的终稿上算出来的，而 x̃i 却是第 di 步的 x̂₀ 预测。好比老师批改的是学生的终稿，批注却写到了第二稿的对应位置上：若第二稿与终稿差不多，这样改还算对路；若差得远（早期步），批注就对不上号。数学上，这等于假设“终稿对第 di 步 x̂₀ 的雅可比 ≈ 单位阵”，是一种直通（straight-through）近似。原版 Self Forcing 没有这个问题，因为它在哪一步停，那一步的 x̂₀ 就是输出本身。

  
在上面的玩具里勾选“各步的 x̂₀ 预测”就能看到：理想老师的 x̂₀ 就是后验均值，第 1 步时落在三点中间，之后逐步向终点收拢。论文没有分析这种错位的影响，表 8 也无法把它分离出来。

训练数据构成

  
  

    
动作标签怎么来的
对长视频直接跑 ViPE 估计相机位姿会严重漂移、尺度塌缩，所以切成 150 帧的重叠片段（重叠 10 帧），分别估计后用重叠窗口对齐尺度再拼接；再把相机运动分解成离散的前后 / 左右平移 + 连续的俯仰 / 偏航角。自家游戏录屏的旋转角速度在同一款游戏里是常数，于是按游戏离线估计角速度、取中位数作为该游戏的标定转速——换句话说，占 80% 的数据里，“连续”旋转实际上接近按游戏量化。

    
质量过滤
按 HunyuanVideo-1.5 的做法，用画质评估模型 + 美学打分，从清晰度、细节保留、噪声与压缩伪影、动态范围、美感五个维度过滤；再检查估计位姿的时间平滑性与物理合理性，剔除相机抖动的片段，以保证动作标签准确。

  







  
09实时：16 FPS 是怎么来的，以及它不代表什么

  
  

    
算得上的
  • 16 帧 ÷ 0.998 s = 16.03 FPS，与“16 FPS”一致。
  • 表中每行的 Speedup / Reduction 与延迟列完全自洽。
  • H20 是面向中国市场的 Hopper 降配卡，稠密 BF16 算力约为 H100 的 15%（公开规格，非论文数据）；8 卡合计大致相当于 1 张多一点的 H100 算力。在这种卡上做到每块 1 秒，工程上不容易。

    
没说清的
  • 分辨率全文没写。
  • 0.998 s 是生成吞吐，不是动作响应延迟；按块粒度，按键到画面约 1–2 秒（§04 估算）。首帧延迟也没报。
  • 是在 rollout 多长时测的？记忆随长度线性增长，每块耗时也会涨。
  • 压缩器、低清分支的重编码是否计入？
  • 表 1/2 的质量分是否在这套实时配置（FP8、LightVAE、SageAttention）下测得？LightVAE 的画质影响没有评估。
  • 基线一行居然还开着 FSDP（训练时的分片策略），关掉就省 0.243 s——起点定得偏宽松。

  







  
10结果：分数、来源，以及该怎么读


  
10.1 WBench 导航子集（158 例）

  
WBench（2605.25874）的五个维度：Qua 画质（VBench 式 5 项 + HPSv3）；Set 场景 / 主体是否符合设定（VLM 打分）；Int 在导航子集上只有 NavScore——用 MegaSaM 估计生成视频的相机轨迹，与动作序列生成的真值轨迹比对，衡量的是“走得准不准”，不是语义事件；Con 一致性（含往返轨迹的回访相似度等 8 项）；Phy 物理（因果合理性 + 视觉合理性）。

  
  

    两处要打折
    
领先很窄，且不是全面领先。均分 83.1 对 Alaya-Evoke-Turbo 的 82.0，只高 1.1；Setting（81.5 对 82.1）和 Quality（81.8 对 81.9）反而略低，Physical 打平（74.0）。优势集中在 Int（导航精度，+0.4 对 EchoWM）和 Con（+0.5 对 AlayaWorld）。没有方差，也没有多次运行。

    
基线数字的来源。论文说“在 WBench 上评测所有模型”，但 WorldPlay 一行（78.1 / 72.2 / 86.8 / 86.9 / 66.3）与 WBench 原文表 2 中 HY-World 1.5（即 WorldPlay 开源版）一列的 Quality、Setting、Consistency、Physical 四项完全相同，只有 Interaction 不同（86.8 对 87.5）。可能是直接引用并抄错一格，也可能只重跑了导航项。无论哪种，都应该说明来源。WBench 原文还指出，一致性分与动态程度负相关（r = −0.56），高一致性有一部分来自“画面动得少”。

  


  
10.2 RevisitBench：自建的回访一致性测试

  
200 条回环轨迹（50 条 10 秒 + 150 条 30 秒），从 WBench 和自家验证集中挑选初始画面。每条轨迹：前半段随机采离散移动和连续旋转，后半段把前半段的动作序列倒过来执行，让模型回到起点；比较回访帧与原帧的 PSNR / SSIM / LPIPS（2D）和 MEt3R（3D 多视图一致性）。

  
  

    为什么要打折
    
RevisitBench 的轨迹结构——“前半段随机、后半段原路倒回”——和自家训练集里 5 万段 UE 回环数据的结构（“后半段精确倒放前半段相机路径，动作持续 1–5 秒随机”）是同一种东西。WorldPlay2 在训练中大量见过这种轨迹先验，基线未必见过。再加上基线的动作接口各不相同（相机位姿、离散键……），怎么把同一条动作序列转成各基线的输入，论文没交代。论文把基线的失败归因于滑窗遗忘（Lingbot-World-V2、EchoWM）、位姿漂移导致检索出错（WorldPlay）、显式 3D 的尺度歧义（AlayaWorld、Alaya-Evoke-Turbo）——这些解释都说得通，但当前实验无法把它们与“训练分布匹配”区分开。更中立的对照是 WBench 自带的往返回访一致性（属于 Con 维度），而在整个 Con 维度上 WorldPlay2 只领先 0.5。

打分向量 g 在走完 4 步的终稿上计算，却施加在第 di 步的 x̂₀ 预测上（算法 1 第 23–24 行）。第 di 步越早，x̂₀ 与终稿差得越远（见 §07 玩具）。这相当于假设终稿对 x̂₀(d) 的雅可比为单位阵。原版 Self Forcing 没有这种错位。它可能恰恰是有效的（相当于要求每一步的 x̂₀ 都向终稿方向修正），但论文没有讨论，也没有对比“只在最后一步回放”等替代方案。

      
补：di 固定为最后一步 vs 随机步的对比；报告 x̂₀(d) 与终稿的距离随 d 的变化。

补：同一测试集上报告多步 AR 模型、PDD 后、DMD 后三个阶段的事件分。

    


    
D7记忆的关键实现细节缺失，复现不了

      
没有给出：sink 与 tmp 的长度；压缩段是否与它们重叠；记忆 token 的位置编码（前作专门设计了时间重排 RoPE）；推理时压缩 token 是否进 KV cache（正文只笼统提到用了 KV caching）；低清分支在推理和 rollout 时如何获得 xlr（似乎需要“解码 → 缩小 → 重新编码”），开销是否计入 0.998 s；蒸馏时压缩器是否继续训练；老师与学生的压缩器权重是否真的“共享”。

      
补：给出记忆配置表与推理时序图；报告压缩器与重编码的耗时。

    


    
D8“长时程”被蒸馏视界框住，超出 320 潜帧后的表现未知

      
蒸馏 rollout 320 潜帧（1277 帧）；展示的最长样例为 1405 帧（352 潜帧，1.1 倍视界）；RevisitBench 最长 30 秒（按 16 FPS 约 121 潜帧）。记忆仍线性增长（只是斜率变为约 1/32），每块耗时随长度增长多少没有报告，表 4 在多长的 rollout 上测也没说。作者在局限性里承认无限时长是开放问题，但正文的“long-horizon”叙述没有给出边界。

      
补：2×、4× 视界的质量曲线与每块延迟曲线。

    


    
D9“实时”的口径：分辨率未写，吞吐 ≠ 响应延迟，评测配置不明

      
全文没有写分辨率。0.998 s/块是生成吞吐；按块粒度，按键到画面约 1–2 秒（§04 的估算），首帧延迟也没报。生成耗时与播放时长几乎相等，没有缓冲余量。LightVAE 贡献了 3.4 倍提速，但它对画质的影响没有评估；表 1/2 的分数是否在 FP8 + SageAttention + LightVAE 的实时配置下测得，也没说明。

      
补：写明分辨率；报告按键到画面的端到端延迟；在实时配置下重跑表 1。

    


    
D10事件的时间粒度与字段定义前后不一

      
正文说三个字段（scene / character / event），附录模板有四个键（多一个 UI）。事件按 5 秒窗口标注，模型一块只有 16 帧（按 16 FPS 播放约 1 秒）：训练时 5 秒标签怎样分配给块、推理时一条事件指令对几块生效，都没交代。还有一个设计上的问题：“下起大雨”这种事件发生之后，世界状态已经变了，scene 字段是否要改写成雨天？模板要求 scene 只写静态内容、按整段视频写一次，那么事件后的新状态由谁来“记住”——只能靠视觉记忆。对一篇以“精确响应”为卖点的论文，这些都是关键细节。

      
补：说明 UI 字段的去向；给出事件到块的对齐规则与推理时的生效规则。

    


    
D11WBench 基线来源混合，且领先幅度窄

      
WorldPlay 一行有四项与 WBench 原文的 HY-World 1.5 完全相同，Interaction 却是 86.8 对 87.5；其余基线是否重跑、用什么设置，没有说明。均分只领先 1.1，Setting 与 Quality 略低于 Alaya-Evoke-Turbo，Physical 持平，无方差。

      
补：注明每个基线分数的来源（引用 / 重跑）与重跑设置；多种子方差。

    


    
D12“约 32 倍压缩”只对中间段成立

      
sink 与 tmp 很可能保持全分辨率（论文没写）。在“全分辨率、sink = tmp = 4 潜帧”的假设下，320 潜帧时有效压缩约 18×；视频越短越低。论文把 32× 当作整体序列的缩减倍数来表述。

      
补：报告不同长度下的实际记忆 token 数。

    


    
D13动作标签与动作对齐的细节

      
占 80% 的游戏录屏，旋转速率按游戏取中位数标定，“连续”旋转事实上接近量化。1 个潜帧覆盖 4 帧，帧内按键不一致时怎样聚合没说。“去掉相机位姿无可见退化”没有定量证据（前作表 5 显示单用离散键远差于连续位姿，不过 v2 保留了连续的俯仰 / 偏航）。“视角”作为动作，是否支持 rollout 中途切换第一 / 第三人称也没交代——WBench 有“视角切换”评测，论文没报。

      
补：有无相机位姿的定量对比；动作聚合规则；视角切换评测。

    


    
D14记号与伪代码不严谨

      
式 (6) 的回归目标写成 sg(Nθ(…))，与学生同名同参数；按 PDD 原文应是冻结的老师。算法 1 第 19 行算的是每段的 gb，第 24 行用的却是每块的 gi。按式 (5) 的约定 v = ε − x，x̂₀ = xσ − σv，于是 g = vfake − vreal = (x̂0,real − x̂0,fake)/σ；对 MSE(x̃, sg(x̃ − g)) 做梯度下降会让 x̃ 沿 −g 移动，即远离真实分布——符号反了（实现大概率没问题，是伪代码写反）。DMD 常用的归一化项也省略了。PDD 输出的是分块平均速度，“CleanPrediction”在这种输出下如何定义也没说。

      
补：统一记号；给出与实现一致的伪代码。

    


    
D15PDD 在 AR + 记忆场景下的超参与流程未给

      
K（块数）、C（每块子区间数）、老师用欧拉还是中点法、PDD 阶段的历史用真视频（teacher forcing）还是自展开，都没说。PDD 原文的实验全是双向模型（ImageNet-256 类条件生成、Qwen-Image 文生图、Wan2.1 与 LTX-2.3 文生视频），大规模实验用的是无数据训练；没有自回归或带记忆的设置。

      
补：PDD 阶段的配置表。

    


    
D16训练数据以游戏录屏为主，“强泛化”只有定性证据

      
全部训练数据的 80%（导航数据的 81%）是自家游戏录屏，真实世界视频只占 7%；跨场景、跨角色“强泛化”的说法只有图示支持。代码、权重、RevisitBench、事件测试集都没发布（项目页写 coming soon）。

      
补：按数据来源（真实 / 游戏 / UE）拆分的评测；发布测试集。

    


    
D17训练超参全面缺失

      
各阶段迭代数、学习率、batch、GPU 数、评论家更新频率、是否使用 CFG——全都没有。前作 v1 的附录还给了这些。

      
补：各阶段超参表。

    

  







  
13结论、做对的地方与启示

  

    

      
做对的地方

      
    
        
  • 记忆与蒸馏一起设计。压缩记忆同时降低推理成本和老师打分成本，让“带记忆的老师 + 长 rollout”的 DMD 能按段线性扩展——这是对 Context Forcing 最自然、最有用的推进。
    • 
        
  • 把 rollout 与反传解耦。每块走满 4 步再写进记忆，梯度逐块回放。改动很小，直击“半成品写进记忆”的问题，显存也可控。
    • 
        
  • 用 PDD 做少步初始化。给 DMD 一个“已经会 4 步出图”的起点，表 8 里这是贡献最大的一项。
    • 
        
  • 系统优化表如实给出每一项的收益，清楚暴露出 VAE 才是延迟大头。
    • 
        
  • 字幕模板、数据构成完整公开，可直接复用；1 万段事件数据就能解锁事件能力，这个观察对做数据的人有价值。
    • 
      

    

    

      
对交互式世界模型的启示

      
    
        
  • 记忆的形态决定能蒸多长。如果老师看不了学生的记忆，就只能在短窗口里监督；压缩记忆让“老师看到的历史 = 学生看到的历史”在长视界上变得可承受。
    • 
        
  • 吞吐 ≠ 交互。块长 16 帧意味着按键到画面约 1–2 秒。要真正“跟手”，需要更小的块、按潜帧注入且可流水的动作，或者投机式生成。
    • 
        
  • 结构化字幕是一种很便宜的“世界状态分解”。但要证明它有效，需要与“同样规则的自由文本”做对照。
    • 
        
  • 长时程一致性的上限 = 压缩器保住的信息。TinyHistory 的消融显示空间 4× 压缩比时间 4× 更伤身份细节，这也会限制回访时的细节保真。
    •
